# 홈 데이터 운영 배포와 복구

개인 A/B에 홈 요약·글 위치 SQL 005~007과 방문 SQL 008, `visit-counts` Edge와 화면을 배포한다. 중앙 함수·SQL·Pages는 변경하지 않는다. 홈 데이터 Step 6의 45개 검사 통과를 선행 조건으로 확인했다.

## 순서

1. A/B 원격 main의 별도 체크아웃과 배포 전 커밋을 확보한다. public 테이블 전체·개인 관리자/회원 사이트 연결, 중앙 회원/사이트/바인딩 및 기존 개인 SQL 함수 정의를 비공개 파일로 백업한다.
2. 기존 개인 Supabase·중앙 사이트·회원 작성 활성화 설정을 유지하고 새 런타임을 복사한다. `pipe.sh`와 기존 작업 디렉터리의 무관한 변경은 배포에 포함하지 않는다.
3. `home-data` 설치 도구의 dry run·실행·재실행을 검증한다. 개인 SQL → 최초 secret 생성 또는 보존 → Edge 배포 → 공개 조회 확인 → 활성화 파일 순서다. Pages를 공개하기 전에 기존 콘텐츠·설정·회원 연결의 보존을 확인한다.
4. Pages 빌드·산출물 검사를 통과한 체크아웃만 일반 커밋/push로 배포한다. GitHub Actions 성공과 제공 파일의 바이트 일치를 확인한다.
5. 실제 공개 홈·글 주소·로그인/이동·방문 중복을 검증한다. 필요한 임시 콘텐츠는 UUID와 실행 ID를 비공개 journal에 먼저 기록하며, 같은 ID/내용의 글만 정리한다. 검증 방문 수는 되돌리지 않는다.

## 복구

화면 장애는 각 사이트의 배포 전 커밋을 별도 checkout에서 빌드해 후속 복구 커밋으로 배포한다. force push는 하지 않는다. 또는 `home-data-config.js`의 `enabled:false`를 배포해 새 홈 API 호출을 중단한다. 구버전 설정의 수동 숫자는 실제 통계로 합산하지 않는다.

추가 SQL은 기존 콘텐츠와 호환되므로 화면을 복구해도 우선 유지한다. 기존 콘텐츠 테이블을 백업으로 일괄 덮어쓰거나 삭제하지 않는다. 새 방문 테이블·일별/전체 집계·중복 키와 `MINIHOMPY_VISIT_SECRET`은 보존한다. secret을 재생성하거나 활성 날짜 중복 키를 삭제하면 중복 집계될 수 있다.

함수 복구가 필요하면 배포에 사용한 소스 커밋에서 `visit-counts`를 동일한 기존 Secrets로 다시 배포한다. 최초 배포 전에는 이 함수가 없으므로 기능 비활성화를 우선한다. 기존 SQL 함수 복원이 실제 필요할 때만 비공개 백업의 해당 함수 정의를 검토해 적용하며, 방문 기록이나 신규 콘텐츠를 과거 시점으로 돌리지 않는다.

비공개 백업/체크아웃/journal 위치: `~/.local/state/minihompy-deployment/home-data-20260923/` (디렉터리 0700, 백업 파일 0600). 공개 배포 커밋·검증·정리 결과는 [Step 7 기록](verification/home-data-step7/README.md)에 남긴다.
