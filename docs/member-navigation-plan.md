# 미니홈피 사이 이동과 사용자 상태 표시 — 실행 계획

상태: Step 1~5 완료. Step 6 미착수. 2026-09-23.
대상: [백로그 2번](backlog.md). 사용자가 Step별로 순차 실행을 요청한다.
저장소: 개인 사이트 `cyworld`, 중앙 서버 `minihompy-central`.
선행 조건: [회원 작성 기능 Step 1~7](member-writing-plan.md) 완료. 현재 문서상 운영 배포·검증까지 완료되어 있다.

## 현재 구현과 부족한 부분

- `visitor-identity.js`는 검증된 방문자의 중앙 회원 ID, handle, 표시 이름, 홈페이지 주소를 받는다. 방문 중인 사이트의 `siteId`는 회원 ID와 다른 식별자다.
- 중앙 `identity-api/handler.js`의 `/directory`는 handle 일치 또는 부분 검색을 지원한다. 활성 회원의 활성·검증된 홈페이지만 반환하지만, 검색어 없는 목록·페이지 탐색·랜덤 방문과 사이트 ID로 홈 주인을 확인하는 전용 계약은 없다.
- `comments.js`, `views/guestbook.js`에는 회원 작성자 이름 링크가 있다. 현재 글에 저장된 홈페이지 주소를 사용하며, 방명록의 집 아이콘은 장식이다.
- `index.html`의 ‘내 미니홈피’·‘랜덤’, `views/home.js`의 ‘파도타기’는 이동 기능이 없다. 관계 영역에는 고정 ‘사촌’ 문구가 있고 일촌신청도 사용자 상태와 무관하게 표시된다.
- 기존 회원 작성 기능은 계정 전환·로그아웃·초안·권한을 관리한다. 이번 이동 기능이 별도의 로그인 상태나 작성 권한을 만들면 안 된다.

## 범위와 기본 정책

- ‘내 미니홈피’는 중앙에서 확인된 로그인 회원의 등록 홈페이지로 이동한다. 비로그인 상태에서는 로그인 안내를 제공하고 기존 로그인 흐름에 연결한다. 확인 중·오류 상태를 비로그인과 구분한다.
- 본인 홈 여부는 **방문자 중앙 회원 ID와 현재 사이트 소유자의 중앙 회원 ID**로 판단한다. 이름·URL 문자열·개인 Supabase UUID·로컬 관리자 여부로 추정하지 않는다. 화면의 본인 표시는 관리 권한을 부여하지 않는다.
- 방문자와 홈 주인은 각각 표시 이름과 handle로 구분한다. 같은 이름이어도 누구의 홈을 누가 방문했는지 알 수 있게 한다.
- 작성자 방문은 중앙 회원 ID로 조회한 최신 활성·검증된 홈페이지를 사용한다. 글에 저장된 이름/주소는 과거 기록이며 현재 이동 대상의 근거로 단독 사용하지 않는다. 익명 글을 이름으로 회원과 연결하지 않는다.
- 파도타기는 우선 중앙에 등록된 공개 회원 목록과 handle 검색으로 제공한다. 일촌 목록처럼 표현하지 않는다. 랜덤은 현재 사이트를 제외한 활성·검증된 사이트 중 선택하며, 첫 검색 결과 몇 개만 무작위로 고르는 방식은 쓰지 않는다.
- 고정 ‘사촌’과 실제 데이터 없는 일촌 권유 문구를 제거한다. 관계 기능 도입 전에는 본인 홈/다른 회원의 홈 등 확인 가능한 상태만 표시하고 일촌신청 동작은 노출하지 않는다. 신청·수락·관계 표시의 실제 구현은 백로그 5번이다.
- 기본 이동은 같은 탭으로 한다. 링크의 새 탭 열기 등 기본 브라우저 사용성을 유지하며, 기존 미저장 내용 확인을 우회하지 않는다. 일반 이동 URL에 access token이나 회원 작성 세션을 넣지 않는다. 목적지의 기존 중앙 방문자 확인 흐름을 재사용한다.
- 화면 확대, 홈 통계, 전체 검색, 글 주소 체계, 초안 저장 기능의 확장은 포함하지 않는다. ‘메인’·‘바로가기’ 메뉴의 별도 서비스도 이번 범위에 추가하지 않는다.

## Step 1. 중앙의 홈 소유자·이동 대상 조회 기반

완료: 중앙 조회 API·읽기 RPC와 [API 계약 v1](member-navigation-contract.md). 실제 SQL 이동 검사 7개 그룹 및 중앙 전체 13개 스위트 통과. [검증 기록](verification/member-navigation-step1/README.md). 운영에는 적용하지 않았다.

중앙 저장소 중심. 후속 화면이 사용할 데이터 계약과 읽기 API를 함께 완성한다.

- 현재 사이트 ID로 공개 소유자 정보와 등록 홈페이지를 조회하는 계약을 구현한다.
- 회원 ID로 최신 이동 대상을 조회한다. 작성자 여러 명을 중복 제거해 제한된 건수로 조회할 수 있게 하여 글마다 개별 요청이 발생하지 않도록 한다.
- 기존 `/directory` 검색 호환성을 유지하면서 목록·페이지 탐색을 추가하고, 현재 사이트를 제외한 랜덤 대상 조회를 구현한다. 정확한 경로·응답·페이지 방식은 이 단계에서 문서화한다.
- 반환 정보는 공개 회원 ID·사이트 ID·handle·표시 이름·홈페이지 등 필요한 필드로 제한한다. 비활성/미검증 대상, 잘못된 입력, 대상 없음과 서버 오류를 구분한다.
- 모든 이동 경로에 동일한 활성·검증 정책과 HTTPS 주소 검사를 적용한다. 검색/목록/일괄 조회의 입력 크기를 제한한다. 비밀번호·인증 바인딩·개인 프로젝트 비밀값은 반환하지 않는다.

완료 기준: 소유자 조회, 최신 주소 변경, 비활성/미검증 제외, 페이지 간 중복·누락, 랜덤의 현재 사이트 제외와 대상 없음 검사가 통과한다. 기존 directory 및 방문자 인증 테스트도 통과하고 API 계약이 기록된다. 운영에는 배포하지 않는다.

## Step 2. 공통 사용자 상태와 ‘내 미니홈피’ 연결

완료: 공통 사용자 상태 모듈, 방문자/홈 주인 표시, 최신 내 홈 주소·중앙 로그인 진입, 고정 관계/신청 문구 제거. 상태·데스크톱/모바일 UI·기존 방문자/관리자 인증·Pages 검증 통과. [검증 기록](verification/member-navigation-step2/README.md). 운영에는 적용하지 않았다.

개인 저장소 중심. 공통 상태 처리와 가장 기본적인 이동 한 가지를 연결한다.

- 기존 중앙 방문자 상태와 Step 1의 홈 소유자 조회를 조합하는 공통 모듈을 만든다. 본인/다른 회원/비로그인/확인 중/확인 실패를 구분하고 로컬 관리자 상태는 별도로 유지한다.
- 상단에 방문자와 홈 주인을 구분해 표시하고, 로그인한 회원의 ‘내 미니홈피’를 최신 등록 주소에 연결한다. 비로그인에는 기존 로그인 진입을 제공한다.
- 미등록·비활성 사이트 및 중앙 장애 시 확인되지 않은 본인 표시나 오래된 계정 링크를 남기지 않고 안내·재시도를 제공한다. 상태가 불확실하면 자동 이동하지 않는다.
- 고정 ‘사촌’과 실제 관계처럼 보이는 문구를 정리하고 일촌신청을 숨긴다. 향후 관계 기능이 붙을 지점을 문서화한다.
- 계정 전환 시 진행 중 조회와 캐시를 무효화하여 이전 계정의 늦은 응답이 화면을 덮지 못하게 한다.

완료 기준: A→A, A→B, 비로그인→B, 동일 이름의 A/B, 로컬 관리자와 중앙 방문자가 다른 경우에 상태와 이동 주소가 맞다. 확인 중/오류는 비로그인과 구분되며 기존 로그인·관리 권한을 변경하지 않는다.

## Step 3. 방명록·댓글 작성자 방문 통일

완료: 공통 작성자 이름·집 링크, 최신 홈페이지 일괄 조회, handle 표시, 실패·비활성·재시도와 오래된 응답 차단. 작성자 방문 데스크톱/모바일 검사 및 기존 회원 방명록·댓글 SQL 권한 검증 통과. [검증 기록](verification/member-navigation-step3/README.md). 운영에는 적용하지 않았다.

개인 저장소 중심. 기존 이름 링크를 공통 이동 정책에 맞추고 집 아이콘까지 연결한다.

- 방명록과 게시판·사진첩·다이어리·방명록 댓글에서 회원 ID 기반 최신 홈페이지 조회를 공통으로 사용한다.
- 작성자 이름과 집 아이콘이 같은 대상으로 이동하게 한다. 댓글에도 접근 가능한 방문 표시를 제공한다. handle을 통해 같은 이름의 작성자를 구별할 수 있게 한다.
- 익명/기존 로컬 작성자는 검증된 중앙 연결이 없으면 임의의 홈페이지 링크를 만들지 않는다. 탈퇴·비활성·주소 조회 실패는 이동 불가/재시도로 표현하고 과거 주소로 자동 우회하지 않는다.
- 공개 프로필 조회가 글 본문 표시를 막지 않게 하고, 페이지 이동/계정 전환 중 오래된 조회가 새 목록에 적용되지 않게 한다.
- 미저장 입력이 있는 상태에서 링크 이동을 취소하면 입력이 유지되는지 확인한다. 기존 글의 작성자·본문·권한 데이터는 변경하지 않는다.

완료 기준: 방명록과 네 종류 댓글에서 이름/집 링크, 동명이인, 주소 변경, 비활성 회원, 익명 작성자를 검증한다. 기존 수정·삭제·비밀글 권한과 미저장 내용 확인이 유지된다.

## Step 4. 파도타기와 랜덤 방문

완료: 회원 목록·handle 검색·다음 페이지, 현재 홈 구분과 랜덤 실제 이동, 오류·재시도·초안 보호·키보드/모바일 처리. 중앙 SQL 및 Step 2~3 회귀, 새 UI 검사와 Pages 검사 통과. [검증 기록](verification/member-navigation-step4/README.md). 운영에는 적용하지 않았다.

개인 저장소 중심. Step 1 API와 Step 2 공통 이동 처리를 이용한다.

- ‘파도타기’를 회원 목록·handle 검색·다음 페이지 탐색이 가능한 화면에 연결한다. 이름·handle·현재 홈 표시로 대상을 구분하고 선택하면 해당 홈페이지로 이동한다.
- 검색 중·결과 없음·중앙 오류·재시도와 이전 검색 응답의 무효화를 처리한다. 일촌 전용 목록이라는 오해가 없게 안내한다.
- ‘랜덤’을 서버가 선택한 실제 이동 대상에 연결한다. 현재 사이트 제외, 후보 0개/1개, 중복 클릭, 요청 실패를 처리한다.
- 목록 선택과 랜덤 이동에서도 기존 미저장 내용 확인을 유지한다. 키보드 선택·닫기·포커스 복귀와 모바일 터치 사용성을 구현한다.

완료 기준: 등록 사이트 수가 0/1/여러 개인 경우, 여러 페이지의 결과, 검색 경쟁 응답, 오류·재시도를 검증한다. 랜덤은 현재 홈으로 돌아오지 않고, 이동할 곳이 없으면 그 이유를 표시한다.

## Step 5. A/B 이동과 인증 수명주기 통합 검증

완료: 서로 다른 A/B/중앙 origin의 실제 로그인·PKCE·방문 티켓·이동 통합(데스크톱/모바일), 회원 작성 SQL·브라우저 수명주기 및 기존 UI 회귀 통과. 방문 기록 중복·오래된 표시·재확인 초안 보호를 보완했다. [검증 기록과 표시 재확인 정책](verification/member-navigation-step5/README.md). 운영에는 적용하지 않았다.

두 저장소의 구현을 로컬 통합 환경에서 검증하고 결함을 보완한다.

- 서로 다른 사이트/저장소 영역을 갖는 A/B 환경에서 A 로그인 → A 홈 → B 홈 → 내 미니홈피 → A 홈을 검증한다. 목적지에서도 A를 인식하고 B 관리 권한을 얻지 않는지 확인한다.
- 작성자 방문·파도타기·랜덤의 실제 화면 이동, 새 탭·새로고침·뒤로가기와 기존 방문 티켓 복귀 흐름을 검증한다.
- A 로그아웃 → B 로그인, 다중 탭, 인증 만료, 중앙 장애, 늦은 응답에서 이전 사용자 상태와 이동 주소가 남지 않는지 확인한다.
- 기존 회원 작성 기능의 초안 보호·비밀글 DOM 정리·권한 검사와 충돌하지 않는지 회귀 검사한다. 필요한 보완만 이번 범위에 포함한다.
- 데스크톱/모바일과 키보드 조작을 확인하고 재현 가능한 검사 및 결과를 남긴다.

완료 기준: 이동·사용자 상태의 통합 검사와 영향받은 기존 인증/작성 회귀 검사가 통과한다. 확인 실패를 로그인 성공이나 본인 홈으로 잘못 표시하지 않는다. 아직 운영에는 배포하지 않는다.

## Step 6. 설치·업그레이드와 실제 A/B 배포 검증

검증된 결과를 운영에 반영하는 단계다. 앞 단계가 모두 완료되어야 착수한다.

- 신규 설치·기존 사이트 업그레이드에서 공통 모듈과 설정이 배포 산출물에 포함되게 한다. 필요한 설정/스키마 변경이 있는 경우에만 설치 절차와 마이그레이션을 추가한다.
- 중앙을 먼저 배포하고 기존 개인 화면과의 호환성을 확인한 뒤 A/B 화면을 배포한다. 복구할 버전과 절차를 기록한다.
- 실제 A 계정으로 A/B 홈 표시, B에서 내 홈 이동, 작성자 링크, 파도타기·랜덤을 검증한다. B 계정 전환·비로그인 상태도 확인한다.
- 기존 회원 등록·사이트 연결·콘텐츠를 보존한다. 작성자 방문 검증에 테스트 콘텐츠가 필요하면 해당 실행에서 만든 항목만 정리한다.
- 배포 버전·검증 결과를 기록하고 백로그 체크박스를 실제 완료 범위에 맞게 갱신한다. 실제 일촌 관계는 백로그 5번의 미완료 의존성으로 명시한다.

완료 기준: 중앙/A/B의 배포 버전과 실제 이동·상태 표시가 확인되고 기존 인증/작성 기능이 유지된다. 테스트 데이터 정리가 끝난다. 백로그 2번의 이동과 임시 관계 표시 정리는 완료하되, 실제 관계 표시까지 완료했다고 기록하지 않는다.

## 순차 실행 규칙

- 각 Step을 요청받으면 선행 Step의 완료 기록과 구현·검증 근거를 먼저 확인한다. 미완료이면 작업을 시작하지 않고 부족한 항목을 알린다.
- 각 Step은 해당 범위의 코드·문서·검증까지 마친 후 상태를 갱신한다. 다음 Step을 자동으로 실행하지 않는다.
- Step 1~5는 로컬 구현·검증, 운영 배포는 Step 6에서 수행한다. 운영 배포가 필요한 단계는 배포/검증 실패를 남긴 채 완료 처리하지 않는다.
- 후속 단계에서 계약 변경이 필요하면 변경 이유·하위 호환성과 영향을 기록한다. 검증 기록은 `docs/verification/member-navigation-stepN/`에 남긴다.
