# 미니홈피 이동 조회 API 계약 v1

2026-09-23. [실행 계획 Step 1](member-navigation-plan.md)의 로컬 구현 계약.
중앙 구현: `minihompy-central/supabase/functions/identity-api/navigation.js`, 기존 `handler.js`, `202609230003_member_navigation.sql`.

## 공통 규칙

- 아래 경로는 중앙 `identity-api` 기준 상대 경로다. `/identity-api` 및 `/functions/v1/identity-api` 접두어 모두 지원한다.
- 읽기 전용 GET이며 중앙 세션/비밀번호/작성 토큰을 요구하지 않는다. 기존 등록 origin CORS 정책을 유지한다. 응답은 `Cache-Control: no-store`이다.
- 공개 프로필 조회는 인증 증거나 관리 권한이 아니다. 화면의 본인 여부는 기존 검증된 방문자 `profile.id`와 조회된 홈 소유자 `item.id`를 비교한다. `site_id`와 회원 `id`는 다른 식별자다.
- 활성 중앙 회원에 속한 활성·검증된 사이트만 이동 대상으로 반환한다. 홈페이지는 HTTPS이며 검증된 `origin + base_path`와 일치해야 한다(마지막 `/` 생략 허용). 로그인 URL, 다른 origin/경로, 사용자 인증 정보, query/hash, HTTP 주소는 반환하지 않는다. 포트가 있으면 1~65535 범위다.
- 새 API의 공개 항목은 `id`, `site_id`, `handle`, `display_name`, `homepage_url` 다섯 필드뿐이다. 개인 Supabase 식별/인증 정보와 비밀번호는 반환하지 않는다. `id`는 중앙 회원 ID다.
- 회원 ID와 사이트 ID는 UUID 형식 검사를 거친다. 일괄 입력은 대소문자 정규화 후 중복 제거한다. 이름으로 회원을 추정하지 않는다.
- 비활성/미검증/미등록 대상을 구별해 공개하지 않는다. 클라이언트는 기존 글의 주소나 캐시로 자동 우회하지 않는다.

## 엔드포인트

| 요청 | 정상 응답 | 용도 |
|---|---|---|
| `GET /navigation/site?site_id=<UUID>` | `{ "item": { ...공개 항목 } }` | 현재 홈의 소유자와 등록 주소 |
| `GET /navigation/members?member_ids=<UUID>,<UUID>` | `{ "items": [...] }` | 내 홈 및 여러 작성자의 최신 홈페이지 |
| `GET /directory?limit=20&after=<UUID>&q=<검색어>` | `{ "items": [...], "next_cursor": "UUID 또는 null" }` | 파도타기 목록·handle 검색 |
| `GET /navigation/random?site_id=<현재 사이트 UUID>` | `{ "item": { ...공개 항목 } }` 또는 `{ "item": null }` | 현재 사이트 제외 랜덤 이동 |

`next_cursor`의 빈 값은 문자열이 아닌 JSON `null`이다. 목록 첫 요청에는 `after`를 생략한다. 검색어 없는 `/directory`도 목록을 반환한다.

### 사이트와 회원 조회

- 사이트가 방문 가능한 상태가 아니면 404와 `{ "error": "방문 가능한 사이트가 없습니다." }`를 반환한다.
- `member_ids`는 쉼표로 나눈 1~50개 UUID다. 중복을 포함한 입력 개수 자체를 50개로 제한한다. 반환 순서는 회원 ID 오름차순이며 요청 순서와 다를 수 있다.
- 조회할 수 없는 회원은 `items`에서 제외한다. 모두 없으면 200과 빈 배열이다. 요청 ID와 응답 ID를 대응하여 이동 가능 여부를 판단한다.
- 글에 저장된 작성자 이름/홈페이지는 수정하지 않는다. 이동할 때 사용할 최신 주소만 중앙에서 읽는다.

### 목록과 검색

- `limit`: 1~50의 정수, 기본 20. `after`: 직전 페이지의 `next_cursor`. 활성·검증·주소 필터를 먼저 적용한 후 회원 UUID 오름차순으로 페이지를 구성한다.
- 데이터가 변하지 않는 동안 페이지 사이에 중복·누락이 없다. 동시에 등록/비활성화되는 데이터에 대한 고정 스냅샷은 보장하지 않는다. 새로고침이나 검색어 변경 시 cursor를 초기화한다.
- 검색은 표시 이름이 아닌 handle의 대소문자 구분 없는 부분 일치다. `q` 또는 `query` 중 하나를 사용할 수 있다. 앞뒤 공백 제거 후 2~30자, 원문 최대 100자이며 제어 문자를 거부한다. 페이지 검색의 `%`, `_`는 SQL 와일드카드가 아닌 문자로 취급한다.
- 검색 페이지 요청은 항상 `limit`을 명시한다. `next_cursor`가 null이면 다음 페이지가 없다. cursor는 탐색 위치일 뿐 권한 증명이 아니다.
- 새 조회 경로는 알 수 없는 인자와 중복 인자를 거부한다. 단일 GET 요청으로 데이터 전체를 반환하지 않는다.

### 기존 directory 호환

- 기존 `/directory?handle=...` 및 `/directory?q=...`/`?query=...` 요청(`limit`, `after` 없음)은 기존 `{ items }` 형태와 기존 네 필드(`id`, `handle`, `display_name`, `homepage_url`)를 유지한다. handle 정규화와 검색 최대 10건 정책도 유지한다.
- 기존 검색에도 동일한 활성·검증된 등록 홈페이지 정책을 적용한다. 잘못된 주소가 있는 오래된 행은 반환하지 않는다.
- 예전에는 400이었던 검색어 없는 `/directory`는 이제 최대 20건의 페이지 목록을 반환한다. 기존 호출부는 handle 또는 검색어를 보내므로 기존 로그인 조회 흐름에는 영향이 없다.
- `handle` 정확 조회와 페이지 인자를 섞지 않는다. 회원 ID가 있는 새 화면은 `/navigation/members`를 사용한다.

### 랜덤

- DB에서 전체 적격 사이트 중 현재 `site_id`를 제외한 뒤 `random()`으로 한 곳을 선택한다. 검색 첫 페이지나 브라우저 캐시에서 선택하지 않는다.
- 후보가 하나이면 그 사이트, 없으면 200과 `item: null`이다. 후보가 여럿일 때 연속 요청이 같은 곳을 선택할 수 있다. 현재 사이트 외의 방문 이력 제외는 제공하지 않는다.
- `site_id`는 제외 조건이며 호출자의 소유권 증명이 아니다. 미등록 UUID를 넣으면 제외되는 사이트 없이 후보를 선택한다.
- 서버가 302로 이동시키지 않는다. 클라이언트가 결과를 받아 미저장 입력 확인을 거쳐 이동한다.
- 전체 후보에 대한 무작위 선택은 초기 규모에 맞춘 구현이다. 대규모 등록 시 DB 실행 비용을 측정해 같은 계약을 유지하는 방식으로 개선한다.

## 오류와 권한

- 400: 형식/개수/길이/페이지 조건 오류.
- 403: 기존 CORS origin 정책 위반.
- 404: 단일 사이트 조회에서 방문 가능한 사이트 없음.
- 405: 새 이동 조회 API에 GET 이외 메서드 사용(OPTIONS 사전 요청은 기존 CORS 처리).
- 503: DB 미설정 또는 RPC 조회 실패. 예상하지 못한 서버 예외는 500. 조회 실패를 빈 목록·비로그인으로 해석하지 않는다.
- 오류 응답의 `error`는 문자열이다. 비밀값이나 내부 DB 오류 원문을 포함하지 않는다.
- SQL RPC `private.identity_navigation`은 `service_role`에만 실행을 허용한다. 브라우저의 anon/authenticated 키로 직접 호출할 수 없다. 중앙 서명키 없이 공개 읽기만 가능하고 인증 API의 서명키 검증은 유지한다.

## 적용과 검증

중앙 마이그레이션은 읽기 함수만 추가하며 기존 회원·사이트·콘텐츠 행을 변경하지 않는다. 로컬 검증은 실제 PostgreSQL 호환 PGlite에서 실행한다.

```sh
# minihompy-central 저장소에서
node scripts/verify-member-navigation.mjs
npm test
```

운영 적용은 실행 계획 Step 6에서 **중앙 마이그레이션 → 중앙 함수 → 개인 화면** 순서로 진행한다. 이번 Step 1에서는 운영 DB/함수/Pages를 변경하지 않는다. 기존 배포 스크립트에 새 마이그레이션을 포함하는 작업도 Step 6 범위다.
