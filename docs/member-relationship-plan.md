## 현재 기반과 개발 범위

- 중앙 회원 ID와 사이트 ID, 검증된 홈 소유자 조회, 회원별 최신 홈페이지 조회가 있다. 개인 Supabase UUID와 중앙 회원 ID는 구분해야 한다.
- 개인 `member-writing` 서버는 사이트에 묶인 회원 세션을 검증하고 중앙 `writing-grants/check`로 실제 회원과 중앙 세션의 유효성을 확인한다. 공통 런타임에는 자동 갱신·로그아웃·계정 전환 처리가 있다.
- 상단 관계 영역은 본인/다른 회원의 홈 상태만 표시한다. 실제 관계 저장·신청 API와 관리 화면은 없다. 파도타기는 전체 등록 회원 탐색이며 일촌 목록이 아니다.
- `views/home.js`의 일촌평은 준비 중 안내다. 실제 저장·조회·권한 검사부터 추가해야 한다.
- 공개/나만보기는 이미 구현됐다. **일촌 공개는 이 계획에 포함하지 않는다.** 관계 기능 완료 후 게시물·댓글·사진·홈 집계 등 읽기 권한에 연결하는 별도 계획으로 진행한다.

## 기본 설계와 정책

아래 기본값을 Step 1에서 실제 인증 구조와 로컬 경합 모델 실증을 통해 [상세 계약 v1](member-relationship-contract.md)으로 확정했다. 범위가 바뀌면 후속 Step과 완료 기준도 함께 수정한다.

### 저장 위치와 인증

- **중앙 DB가 회원 쌍의 관계를 단일 원본으로 관리한다.** A/B 개인 DB에 각각 독립적으로 관계를 저장하거나 서로 동기화하지 않는다. 사이트 주소가 바뀌어도 중앙 회원 ID 기준 관계는 유지한다.
- **일촌평 본문은 평이 달린 홈의 개인 DB에 저장한다.** 중앙에는 관계와 권한 판정에 필요한 최소 정보만 둔다. 비밀번호·개인 콘텐츠를 중앙에 모으지 않는다.
- 브라우저 → 방문 중인 개인 서버 → 중앙 서버 경로를 기본으로 한다. 개인 서버가 기존 회원 세션을 검증하고 서버에 보관한 중앙 자격으로 호출한다. 중앙은 그 자격에서 행위자를 결정하며 브라우저가 보낸 UUID·표시 이름을 인증 근거로 사용하지 않는다.
- 기존 작성 grant를 관계 작업에 사용하는 범위와 새 목적 제한 자격의 필요 여부는 Step 1에서 확정한다. 기존 grant의 권한을 무심코 넓히지 않고, 사이트·회원·세션 바인딩과 폐기 검증을 유지한다. 중앙 자격과 서비스 키는 브라우저에 반환하지 않는다.
- 관계 작업에는 중앙 회원 인증이 필요하다. 로컬 관리자 인증만으로 중앙 회원을 대신해 신청·수락할 수 없다. 공통 회원 세션을 재사용하고 메뉴별 ‘회원 확인’ 버튼이나 별도 로그인 저장소를 만들지 않는다.

### 관계와 화면 정책

- 상태는 관계 없음 → 신청 대기 → 일촌이다. 보낸 신청은 취소, 받은 신청은 수락/거절, 성립한 관계는 어느 쪽이든 끊을 수 있다.
- 자기 자신·중복 신청을 거절한다. 반대 방향 신청이 이미 있어도 자동 수락하지 않고 받은 신청을 수락하도록 한다. 동시 신청은 하나의 대기 관계만 남긴다.
- 수락/거절은 수신자, 신청 취소는 발신자만 가능하다. 과거 신청의 늦은 수락/취소가 새 신청을 변경하지 못하도록 요청 ID와 버전을 구분한다.
- 받은/보낸 신청은 당사자만 조회한다. 확정 일촌 목록은 공개를 기본으로 하되 활성 회원의 공개 프로필만 반환한다. 비활성 회원과 사이트 미등록/비활성/미검증 상태의 노출·이동 규칙을 Step 1에서 구분해 고정한다.
- 서버 변경은 한 트랜잭션으로 양쪽 관점에 반영한다. 화면은 작업 완료·관계 화면 진입·탭 복귀 때 재조회한다. 이미 열린 다른 화면의 즉시 실시간 갱신까지 보장하지 않으며, 변경 요청은 항상 최신 서버 상태를 확인한다.
- 신청과 목록 관리는 별도 알림 시스템 없이 접근 가능한 ‘일촌 관리’ 화면으로 제공한다. 전체 회원 파도타기는 유지하고 일촌 목록과 구분한다. 팬 기능·일촌명/상호 별칭·차단·푸시/읽음 알림은 이번 범위가 아니다.

### 일촌평 정책

- 해당 홈 주인과 현재 일촌인 중앙 회원만 새 평을 작성한다. 자기 홈의 자기 평, 익명/비일촌 작성은 허용하지 않는다.
- 공개 짧은 텍스트 목록으로 제공하며 한 회원이 여러 평을 남길 수 있다. 이번에는 작성·삭제를 제공하고 수정·첨부·답글은 추가하지 않는다. 글자 수·페이지 크기·반복 요청 제한은 Step 1에서 고정한다.
- 작성자는 자신의 평을, 개인 사이트에서 검증된 관리자는 해당 홈의 평을 삭제할 수 있다. 일촌을 끊어도 과거 평은 자동 삭제하지 않고 작성자의 삭제 권한도 유지한다. 타인의 평 삭제는 거절한다.
- 새 작성은 개인 서버가 중앙의 현재 관계를 확인해야 한다. 중앙 장애/불명확한 관계를 일촌으로 간주하지 않는다. 이미 저장된 공개 평 읽기는 관계 서버 장애만으로 차단하지 않는다.
- 관계 끊기와 개인 DB 저장은 서로 다른 DB의 작업이다. **작성 허용의 기준 시점과 경합 처리 방식**을 Step 1에서 명시하고 실증한다. 끊기 전에 중앙에서 허가된 진행 중 작성이 나중에 저장될 수 있는지, 허가의 유효 시간·재사용 차단을 계약에 포함한다. 분산 작업을 하나의 원자적 트랜잭션처럼 약속하지 않는다.
- 작성 중 내용은 홈 메뉴를 떠나면 폐기한다. 같은 화면에서 자동 세션 갱신·일시 오류가 발생하면 입력을 유지하고, 로그아웃·계정 전환에는 제거한다.

## Step 1. 관계·인증·일촌평 계약 확정

상태: 완료. 선행 5개 계획의 운영 완료 기록 및 최신 기반 소스 155개 중 실행 코드/계약 일치를 확인했다(백로그 계획 링크 변경 1개 제외). 관계 상태·API·권한·목록·제한·화면 계약과 중앙 허가 후 30초 내 작성 경합 정책을 확정했다. 기존 실제 인증 handler/SQL을 연결한 새 관계 메모리 실증 13개 그룹, 기존 개인 세션 10개·중앙 v2 세션 12개 그룹 통과. [검증 기록](verification/member-relationship-step1/README.md). 운영 미변경, 새 관계 SQL과 실제 다중 연결 경합은 Step 2 이후 범위다.

- 선행 계획의 완료 기록과 현재 구현을 확인한다. 실제 미완료 항목이 있으면 즉시 중단한다.
- `docs/member-relationship-contract.md`에 상태 전이, 권한표, 데이터 소유권, 공개/비공개 응답, 비활성 대상, 페이지 조회, 입력/요청 제한과 오류 규칙을 고정한다.
- 현재 중앙 grant/개인 세션 경로를 조사하고 관계 API의 인증·사이트 바인딩을 설계한다. 개인 서버 설정의 site ID로 대상 홈 주인을 결정하고 임의 대상 지정으로 일촌평 권한을 우회하지 못하게 한다.
- 최소 로컬 실증으로 검증된 회원의 관계 요청, 위조 행위자·다른 사이트 자격 거절, 일촌평 허가와 관계 끊기의 경합을 확인한다. 허가 방식과 장애·응답 유실 시 재시도 계약을 선택한다.
- 일촌 관리 진입점, 받은/보낸 신청, 공개 일촌 목록, 홈 일촌평의 화면 흐름을 문서화한다.

완료 기준: 후속 구현이 추정하지 않아도 되는 API/권한/상태 계약과 인증·분산 경합 실증 결과가 있다. 설계만 남기고 실증을 생략하면 완료가 아니다. 운영은 변경하지 않는다.

## Step 2. 중앙 관계 데이터와 상태 전이

상태: 완료. Step 1 근거·소스 166개 일치를 확인했다. 중앙 migration `202609240001_member_relationships.sql`에 관계/작업 기록/작성 허가/요청 제한과 service 전용 RPC를 구현했다. SQL 권한 19개·독립 PostgreSQL 경합 16개 그룹, 중앙 전체 16개 스위트 및 기존 개인 세션 10개 그룹 통과. [Step 2 검증 기록](verification/member-relationship-step2/README.md). 운영 미적용, HTTP·개인 서버 연결은 Step 3 범위다.

- 중앙 migration과 내부 RPC로 신청·수락·거절·취소·끊기 및 관계/신청/일촌 목록 조회를 구현한다.
- 순서 없는 회원 쌍의 유일성, 발신/수신 구분, 요청 ID·버전, 잠금과 트랜잭션을 적용한다. 직접 테이블 접근으로 내부 권한 검사를 우회할 수 없게 한다.
- 중복 전송·응답 유실에 대응하는 작업 식별자와 결과 확인을 구현한다. 과거 성공 응답이 현재 관계 상태를 덮지 않도록 작업 결과와 현재 버전을 구분한다.
- 일촌평 작성 허가에 필요한 최소 중앙 판정/기록도 확정 계약대로 구현한다. 중앙에 평 본문은 저장하지 않는다.

완료 기준: 실제 SQL 및 독립 연결 경합 검사에서 동시 양방향 신청, 수락↔취소, 거절↔수락, 끊기↔재신청, 과거 요청 재전송이 올바르게 처리된다. 제3자/비회원의 변경과 대기 신청 조회가 차단된다.

## Step 3. 중앙 API와 개인 서버의 회원 인증 연결

상태: 완료. Step 2 소스·근거 178개 일치를 확인했다. 중앙 관계 API·개인 member 전용 중계·공통 세션 기반 repository·명시적 작업 결과 복구를 구현했다. 실제 handler/SQL API 12개·브라우저 소스 VM 5개 그룹, 중앙 전체 16개 스위트·개인 세션 10개 그룹·공통 runtime/client 회귀 및 Pages 검증 통과. [Step 3 검증 기록](verification/member-relationship-step3/README.md). 운영 미적용, 화면은 Step 4 이후 범위다.

- 중앙 관계 API와 개인 서버 중계 경로를 구현하고 브라우저용 repository를 제공한다. Step 2 내부 RPC를 공개 API로 직접 노출하지 않는다.
- 기존 공통 세션의 자동 갱신과 폐기 검증을 재사용한다. 관계 작업은 로컬 관리자 자동 선택 경로와 구분해 중앙 회원 자격으로 실행한다.
- 중앙 자격에서 행위자를 결정하고 대상·site·현재 세션을 검증한다. 비로그인/만료/권한 없음/충돌/요청 제한/중앙 장애를 구분한다.
- 응답 유실은 동일 작업 식별자로 결과를 확인한다. 계정 전환 뒤 오래된 요청을 새 계정으로 자동 재전송하지 않는다. 민감한 신청 응답의 캐시·로그 노출을 방지한다.

완료 기준: 실제 handler와 DB를 연결해 정상 관계 작업, 위조 UUID, A/B 자격 혼용, 로컬 관리자만 있는 경우, 만료/철회, 중앙 장애, 재시도를 검증한다. 기존 방문·로그인·회원 작성 계약도 유지된다.

## Step 4. 현재 홈과의 관계 표시·신청 동작

상태: 완료. Step 3 근거·소스 198개 일치를 확인했다. 현재 홈 관계 표시·공통 창과 신청/취소/수락/거절/끊기, 결과 확인·계정 전환·탭 복귀·미지원 서버 처리를 구현했다. 실제 Chromium 1280px/375px 12개 그룹, 기존 navigation UI 회귀, 실제 API/SQL 12개·client/runtime VM 5개 그룹 및 Pages 검사 통과. [Step 4 검증 기록](verification/member-relationship-step4/README.md). 운영 미적용, 전체 신청 관리·일촌 목록은 Step 5 범위다.

- 상단 관계 영역에 자기 홈/비회원/관계 없음/보낸 신청/받은 신청/일촌/확인 중/실패를 표시한다. 기존 방문자·홈 주인 표시는 유지한다.
- 신청·취소·수락·거절·관계 끊기를 연결한다. 거절/끊기 등의 결과를 명확히 안내하고 중복 클릭과 진행 중 상태를 처리한다.
- 서버에서 확인한 결과로 표시를 갱신한다. 중앙 오류를 ‘일촌 아님’으로 바꾸지 않으며 계정 전환·탭 복귀·늦은 응답을 처리한다.
- 관계 영역에 남은 팬/친구추천 등의 문구가 구현된 기능으로 오해되지 않도록 정리한다. 별도 추천 기능은 만들지 않는다.

완료 기준: A→A, A→B, B→A, 비로그인, 로컬 관리자와 중앙 회원이 다른 경우의 표시·행동이 맞는다. 데스크톱/좁은 화면·키보드에서 조작 가능하고 관계 작업을 위해 추가 회원 확인 버튼을 요구하지 않는다.

## 순차 실행과 기록 규칙

- 요청받은 Step 직전에 이전 Step의 완료 기록·구현·검증 근거를 확인한다. 미완료면 즉시 중단하고 빠진 항목을 알린다. Step 1에는 위 선행 조건을 적용한다.
- 한 번의 요청에서는 해당 Step만 수행한다. 다음 Step은 자동 시작하지 않는다. 이전 단계 결함으로 선행 조건이 성립하지 않으면 임의로 후속 작업과 합쳐 진행하지 않는다.
- 검증 기록은 `docs/verification/member-relationship-stepN/`에 남긴다. 두 저장소의 관련 소스 버전/해시, 명령·결과와 남은 제약을 기록한다. 비밀값·운영 신청 정보·개인 콘텐츠는 기록에 넣지 않는다.
- 이전 검증 이후의 소스 차이를 확인하되, 새 계획/백로그 링크 같은 문서 추가만으로 이전 기능이 미완료라고 단정하지 않는다. 실행 코드·계약 변경으로 검증이 유효하지 않으면 필요한 재검증을 먼저 수행한다.
- Step 1~9는 로컬 설계·구현·검증·배포 준비, Step 10은 운영 적용이다. 완료 상태에 로컬 완료와 운영 완료를 구분한다.
- 기존 미커밋 변경을 보존한다. 이 계획을 작성했다고 기능 체크박스를 완료 처리하지 않는다. 일촌 공개·팬·알림/차단은 별도 후속 작업이다.
