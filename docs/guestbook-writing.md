# 방명록 저장과 방문자

## 기능

- `guestbook_posts`에서 5개씩 조회한다. 과거 `guestbook-data.js` 샘플은 실행하지 않는다.
- 이름(1~20자), 일반 텍스트 본문(1~5,000자), 공개/비공개를 지정한다. [공통 댓글](comments.md)을 지원한다. 신고·개인 미니미 변경은 아직 지원하지 않는다.
- 방문자에게 회원가입/로그인 폼이나 CAPTCHA를 요구하지 않는다. 첫 저장에서만 Supabase 익명 인증으로 브라우저 세션을 만든다. 읽기에는 익명 계정 생성이 없다.
- 다음 방문에는 해당 브라우저의 인증 세션과 닉네임을 재사용한다. 닉네임은 변경 가능한 표시 이름이며 실명/고유 신원/권한 증명이 아니다. 저장된 글의 이름은 변경하지 않는다.
- 쿠키/사이트 데이터 삭제, 시크릿 창 종료, 다른 브라우저/기기로 이동하면 기존 글의 작성자 권한을 복구할 수 없다. 계정 연결/복구 기능은 아직 없다.
- 관리자는 기존 관리자 세션으로 작성한다. 별도 방문자 계정을 만들지 않는다.

## 비공개와 권한

- 공개 글은 누구나, 비공개 글은 작성자와 관리자만 조회한다. RLS가 본문과 행 자체를 필터링하므로 CSS로 숨기는 방식이 아니다. 페이지 개수도 조회 권한이 있는 글을 기준으로 계산한다.
- 작성자만 본문 수정이 가능하다. 작성자와 관리자는 삭제 및 공개에서 비공개로 전환할 수 있다.
- 관리자도 다른 사람의 본문을 수정할 수 없다. 비공개에서 공개로의 전환은 누구에게도 허용하지 않아 관리자 비공개 조치를 작성자가 되돌릴 수 없다.
- 생성 시각, 작성자 ID/이름, 글 번호, revision은 일반 API에서 수정할 수 없다. revision 비교로 동시 수정/삭제 충돌을 처리한다.
- 방문자 신규 글은 10초에 1개, 연속 24시간 창당 20개로 제한한다. 별도 비공개 카운터를 잠가 동시 요청과 글 삭제를 통한 우회를 막는다. 관리자는 작성 빈도 제한을 받지 않는다.
- Auth IP 제한은 새 익명 계정 남발을 완화하고 DB 제한은 기존 계정의 반복 작성을 제한한다. CAPTCHA를 사용하지 않으므로 새 계정을 반복 생성하는 봇에 대한 방어는 약하다. 사용자별 DB 제한만으로 이를 막을 수 없으며 운영 시 가입 수/트래픽을 확인해야 한다.

## Supabase 설정

현재 사용자 접속 주소는 `http://127.0.0.1:5500/index.html#/home`이다.

1. Authentication의 CAPTCHA protection을 끈다. 켜둔 상태에서는 토큰을 보내지 않는 관리자 로그인/익명 인증이 실패할 수 있다.
2. Allow anonymous sign-ins를 켠다. Auth의 가입 IP 제한은 유지한다.
3. 관리자 로그아웃 상태에서 이름과 방명록을 입력하고 저장한다. 별도 확인 창 없이 첫 작성에서 익명 세션을 만든다.
4. 새로고침 후 닉네임/본인 글 권한이 유지되는지 확인한다. 다른 브라우저에서는 비공개 글이 보이지 않아야 한다.

사용자 요청으로 Turnstile 공개 키, 스크립트, 확인 창과 관리자 로그인 CAPTCHA 연결을 제거했다. Cloudflare 설정은 필요하지 않다. 코드 변경만으로 Supabase 대시보드 설정이 바뀌지는 않는다.

공식 자료: [Supabase 익명 인증](https://supabase.com/docs/guides/auth/auth-anonymous).

## 실패와 초안

- 다른 메뉴 이동·문서 이탈 시 미저장 입력을 확인창 없이 폐기한다. 같은 화면의 인증 갱신·저장 실패에서는 메모리 초안을 유지한다. 영구 임시 저장은 하지 않는다. 기억된 닉네임은 초안과 별개다.
- 관리자 로그인/로그아웃 등 역할 변경이나 다른 탭에서 방문자 세션 변경 시 초안과 표시 중인 비공개 글을 지우고 권한을 재확인한다.
- 조회 권한 확인이나 조회 실패 시 과거 비공개 글을 화면에 남기지 않는다.
- 저장 응답 유실 후 재시도는 같은 UUID와 작성자/본문/공개 상태를 확인해 중복 생성을 피한다. 실패 시 무조건 자동 재전송하지 않는다.

## SQL 및 검증

`202609130006_guestbook.sql` 다음에 `202609130007_guestbook_clock.sql`을 적용한다. 두 번째 SQL은 SQL 예약어와 변수 이름의 충돌을 수정하며 기존 데이터는 변경하지 않는다.

사용자가 두 SQL의 실행 성공을 확인했다. CAPTCHA 비활성화/익명 인증 활성화는 별도 대시보드 설정 단계다.

- `scripts/verify-guestbook-db.mjs`: 로컬 PGlite에서 공개/작성자/관리자 권한, 비공개 필터, 타인 본문 변경 금지, 공개 복원 금지, 불변 열, revision, 작성 제한과 창 초기화를 검사한다.
- `scripts/verify-guestbook-writing.mjs`: 모의 Auth/API + 실제 SDK, CAPTCHA 없이 최초 작성만 익명 식별, 닉네임 기억, 초안, 작성/수정/삭제, 관리자 전환, 권한별 비공개 표시, 실패/충돌/응답 유실, 데스크톱/모바일을 검사한다.
- `scripts/verify-admin.mjs`: CAPTCHA 토큰 없이 관리자 로그인을 처리하는지 모의 Auth로 검사한다.
- `scripts/verify-guestbook-live-read.mjs`: 실제 프로젝트 공개 조회만 수행하며, GET 이외 요청을 차단한다. 읽기에서 익명 계정을 만들지 않는다.
- 실제 익명 계정 생성은 프로젝트 소유자가 실제 브라우저에서 확인한다. 자동화는 실제 익명 계정이나 방명록을 만들지 않는다.

- 제한 응답은 10초 간격과 24시간 20개를 구분한다. 간격 제한은 남은 초, 24시간 제한은 남은 시간을 분 단위로 올림하여 `N시간 M분`으로 표시한다. 24시간 창은 기존처럼 첫 작성 시점부터 계산하며 삭제로 카운터가 줄어들지 않는다. 두 제한이 겹치면 24시간 제한을 우선 안내한다.
