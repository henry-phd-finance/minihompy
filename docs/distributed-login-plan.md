# 분산 미니홈피 로그인 구현 계획

작성: 2026-09-23. 대상: `~/cyworld`, `~/minihompy-central`.
현재 로컬 코드와 테스트를 조사한 계획이며 운영 배포 상태는 확인하지 않았다.

## 목표와 계약

- 개인 GitHub Pages는 화면, 개인 Supabase는 계정 인증·콘텐츠·권한을 담당한다.
- 중앙은 고유 handle, 회원 ID, 사이트 주소, Supabase 프로젝트와 소유자 UUID 연결, 중앙 세션에 필요한 최소 정보만 관리한다. 비밀번호와 개인 콘텐츠는 저장하지 않는다.
- B에서 로그인 클릭 → 중앙의 ID 입력 화면 → A의 비밀번호 화면 → A Supabase 인증 → 중앙 세션 생성 → B의 원래 화면으로 복귀한다.
- 중앙 ID 화면과 개인 비밀번호 화면은 같은 레이아웃과 문구를 사용한다. 비밀번호 입력은 개인 사이트에서만 한다.
- B/C는 A를 방문자로 표시하되, 관리자 권한과 글 작성 권한은 해당 사이트의 기존 RLS로 별도 판정한다.
- 중앙 로그아웃은 공통 방문자 세션을 종료한다. 현재 사이트가 자신의 사이트이면 로컬 관리자 세션도 종료한다. 다른 origin에 남은 로컬 세션은 다음 명시적 로그인 때만 재사용한다.

## 확인된 현재 상태

1. 중앙에는 directory, login-intents, activation-tickets, sessions/complete, visits/issue, visits/resolve, sites API와 서명 토큰 기반 구조가 구현되어 있다.
2. `activation-tickets`는 개인 Supabase 인증 증명 없이 입력된 `local_user_id`를 비교하거나 최초 바인딩한다. ID 일치는 로그인 증명이 아니다. TS 운영 진입점과 JS 테스트 구현 모두 해당한다.
3. `POST /sites`는 사이트 소유권 확인 없이 등록한다. origin/homepage/login URL 사이의 일관성 검증도 보완해야 한다.
4. 중앙 서명키 누락 시 코드의 고정 기본값으로 돌아가는 경로가 있다.
5. 중앙 Edge Function에는 ID 입력 HTML이 있으나 GitHub Pages용 `public/login.html`은 없다. 개인 사이트의 `admin-auth.js`가 현재 ID 입력과 중앙 API 호출을 담당한다.
6. 개인 인증 화면은 이메일과 비밀번호를 모두 요구한다. 요구한 ID → 비밀번호 흐름을 위해 개인 사이트에서 handle과 인증 계정의 연결을 처리해야 한다.
7. 중앙 public 페이지는 `.html` 경로인데 개인 방문·로그아웃 URL은 확장자가 없다. 개인의 `/complete.html` 변경은 미커밋이다.
8. `login/index.html`은 `/`로 이동해 저장소 하위 경로를 잃고, 개인 Pages 빌드에도 login 디렉터리가 포함되지 않는다.
9. 로그인 완료 이벤트 처리와 관리자 자동 중앙 연결이 각각 활성화 티켓을 요청할 수 있다. 원래 복귀 사이트를 보존하는 단일 처리가 필요하다.
10. 중앙이 fragment의 `path`에 전체 상대 경로를 보내지만 개인 코드는 이를 hash처럼 취급하므로 원래 메뉴가 HOME으로 바뀔 수 있다.
11. 관리자/방문자 모듈이 같은 버튼을 별도로 갱신하며 관리자 로그아웃은 중앙 세션을 정리하지 않는다.
12. CLI가 handle을 수집하지만 생성되는 방문자 설정에는 포함하지 않는다. 중앙 `.github/` 배포 설정은 미추적이다.
13. 중앙 TS와 JS 구현이 병존하며 검사는 JS를 실행한다. 운영 진입점과의 일치 보장이 필요하다.

## 실행 순서

### 1. 인증·등록 계약 확정 및 중앙 검증 구현

**로컬 구현 완료 (2026-09-23).** 중앙 저장소 `docs/identity-v2.md`에 API 계약과 검증 결과를 기록했다. 개인 Supabase Auth/소유자 RPC 검증, Pages 확인 파일과 트랜잭션 등록, 기존 사이트 재검증, 전용 서명키, 일회성 교환 및 S256 브라우저 검증값을 구현했다. 운영 배포·DB 적용은 하지 않았으며 구형 화면/CLI 연결은 아래 2~4단계에 남는다.

- 클라이언트가 보낸 UUID를 신뢰하는 경로를 제거한다. 등록된 개인 Supabase 프로젝트에서 발급한 access token을 중앙에서 검증하고, 검증된 사용자 ID를 등록된 소유자 UUID와 비교한다.
- 첫 구현은 해당 프로젝트 Auth의 `getUser(jwt)` 기반 검증을 우선한다. 프로젝트 주소와 공개 API 키는 검증된 등록 정보에서 읽고 비밀번호·refresh token·service role key는 중앙으로 보내거나 저장하지 않는다. 검증에 사용한 access token도 저장하거나 로그에 남기지 않는다.
- 익명 계정, 다른 프로젝트의 토큰, 만료·변조 토큰, 소유자가 아닌 계정을 거절한다. CORS는 인증의 대체 수단으로 사용하지 않는다.
- 사이트 등록은 소유권 확인 전 pending 상태로 두고, 개인 Pages의 일회성 challenge와 개인 Supabase 소유자 연결 증명을 확인한 뒤 활성화한다. 기존 등록 정보도 재검증 경로를 제공한다.
- 등록 URL의 HTTPS/origin/base_path/login 경로 일관성을 검증하고 등록·바인딩을 트랜잭션으로 처리한다.
- 중앙 전용 서명키가 없으면 발급을 실패시킨다. intent/activation 교환에는 일회성 ID와 원자적 소비를 적용하고 브라우저 로그인 시도와 연결한다.
- 완료 기준: UUID만 제출하거나 타인/다른 프로젝트의 토큰을 제출해서는 중앙 세션을 만들 수 없다. 미검증 사이트는 로그인 대상으로 활성화되지 않는다.

### 2. 중앙 ID → 개인 비밀번호 화면 구현

**로컬 구현 완료 (2026-09-23).** 중앙 ID/완료 페이지와 개인 비밀번호 페이지, 개인 `owner-login` 함수, 기존 개인 세션 재사용, 단일 활성화 처리, 취소·오류·만료 안내를 구현했다. [API·설정 설명](login-flow.md), [검수 결과](verification/login-step2/README.md). 1280/375px 브라우저에서 A 인증 후 B 게시판 복귀·권한 분리까지 검증했다. 실제 Supabase Auth는 모의 응답이며 운영 함수/Secrets 배포는 4단계에 남는다.

- 중앙 `public/login.html`을 구현하고 개인 로그인 버튼은 중앙 페이지로 이동하도록 바꾼다. Edge HTML과 정적 HTML 중 실제 배포 경로를 단일 기준으로 정한다.
- 개인 `login/index.html`을 실제 비밀번호 입력 페이지로 구현하고 빌드에 포함한다. 중앙과 같은 디자인으로 ID를 유지해 보여준다.
- 개인 Supabase의 현재 이메일 인증과 handle을 연결해야 한다. 권장안은 개인 Supabase Edge Function에서 소유자 계정을 매핑하고 비밀번호 인증을 수행하는 방식이다. 중앙에는 이메일 매핑이나 비밀번호를 보내지 않는다. 함수는 비밀번호를 로그·DB에 기록하지 않는다.
- 개인 함수가 돌려준 정상 세션을 개인 SDK에 설정하고 중앙 검증 단계로 이어간다. 기존 유효 세션은 명시적 로그인 요청에서 재사용한다.
- 자동 중앙 연결과 intent 처리기를 하나로 통합해 티켓 발급과 이동을 한 번만 수행한다.
- 미등록 ID, 비밀번호 오류, 취소, 만료, 재시도를 구현한다. 중앙 연동을 끈 단독 사이트의 관리자 로그인도 유지한다.
- 완료 기준: 사용자가 중앙에서 ID를, 개인 사이트에서 비밀번호만 입력해 원래 B 화면으로 돌아온다. 비밀번호 요청의 목적지는 개인 Supabase뿐이다.

### 3. 방문 인식·복귀·로그아웃 정리

**로컬 구현 완료 (2026-09-23).** 탭별 방문 시도를 로그인·완료·로그아웃까지 연결하고, 성공·실패 모두 티켓을 URL에서 제거한다. 원래 경로 복원 중 라우터 초기화를 대기시키며, 방문자/관리자 버튼을 한 곳에서 갱신한다. 현재 사이트의 개인 관리자 세션과 중앙 세션을 순서대로 종료하고, 장애·저장소 차단 시 오류와 재시도를 제공한다. 서로 다른 A/B/C origin을 사용한 모의 브라우저에서 직접 방문·새로고침·로그아웃·장애 복귀를 검증했다. [검수 결과](verification/login-step3/README.md). 운영 배포와 실제 Supabase 검증은 4~5단계에 남는다.

- visit/login/complete/logout 주소를 실제 정적 배포 경로에 맞추고 저장소 base path를 유지한다.
- 로그인 시도 및 방문 시도의 상관관계를 확인한다. 중앙이 검증해 반환한 경로로 query/hash를 복원하고 성공·실패 모두 URL의 티켓을 제거한다.
- 중앙 복귀 처리와 앱 라우터의 초기화를 조율한다. 루프 방지 가드와 세션 상태를 구분한다.
- 관리자 상태와 공통 방문자 상태를 합쳐 버튼을 한 곳에서 렌더링한다. 로그아웃 직후 로컬 세션 때문에 자동 재로그인되지 않게 한다.
- 중앙 장애·저장소 차단·만료·복귀 실패에 타임아웃과 재시도/원래 사이트 복귀를 제공한다. localStorage 저장 실패를 로그인 성공으로 표시하지 않는다.
- 완료 기준: A가 B/C에서 동일 방문자로 표시되며 B/C의 관리자 권한은 없다. 원래 메뉴 유지, 로그아웃, 새로고침, 직접 방문이 일관된다.

### 4. 설치·배포·기존 사용자 전환

**로컬 구현 완료 (2026-09-23).** 개인 CLI의 신규 설치/기존 DB 등록/기존 사이트 재검증/Pages 검증을 분리하고 소유자 Auth 증명·개인 Secrets/함수 배포·확인 파일·handle 설정 생성을 연결했다. 중앙 함수 배포 사전조건, 양쪽 Pages 산출물 검사, JS 단일 구현과 TS 어댑터 검사, 기존 데이터/세션 전환 안내를 추가했다. [설치·전환 안내](install-and-upgrade.md), [검수 결과](verification/login-step4/README.md). 실제 원격 적용은 5단계에 남는다.

- CLI에 소유자 매핑, 개인 로그인 함수 배포, 등록 challenge 확인, handle 설정 생성을 반영한다.
- 기존 활성 사이트와 바인딩을 덮어쓰지 않는 마이그레이션 및 재검증 절차를 만든다. 기존 중앙 세션의 유지/폐기 정책도 적용한다.
- 중앙 Pages 워크플로우를 추적 대상으로 정리하고 public 페이지 및 개인 login 페이지가 실제 산출물에 포함되는지 검사한다.
- TS를 운영·검사 공통 기준으로 사용하거나 JS 생성 절차와 차이 검사를 고정한다.
- README와 검수 문서에서 과거 구조를 분리하고 새로운 설치·로그인 계약을 반영한다.

### 5. 두 사이트 통합 검증과 배포 순서

**진행 중 (2026-09-23).** 실제 중앙 DB에서 서로 다른 A/B origin·Supabase 프로젝트를 확인하고 운영 사전점검을 실행했다. 최신 배포 검사 28개 중 6개 통과이며 중앙 DB/Pages와 개인 로그인 화면은 전환 전이다. 두 개인 프로젝트 Management 권한(현재 403), B 저장소 쓰기 권한, 개인 로그인 정보가 없어 원격 전환/실제 로그인은 대기한다. 로컬 A/B/C 통합·계정 전환 검사를 통과했고 초기 로딩 중 방문 기록이 대체되는 복귀 문제를 수정했다. 중앙 저장소 `docs/verification/login-step5/README.md`와 JSON 보고서에 근거 및 재개 명령을 기록했다. 운영 완료로 판정하지 않았다.

- 먼저 실패하는 기존 클라이언트 모의 브라우저 환경을 복구하고, 단계별 변경마다 관련 회귀 검사를 추가한다.
- 실제로 서로 다른 두 origin과 서로 다른 Supabase 프로젝트를 사용하는 테스트 환경에서 검증한다. 같은 origin의 경로만 바꾼 검사는 충분하지 않다.
- 필수 시나리오: B에서 A 로그인/복귀, A에서 B 직접 방문, 추가 사이트 방문, 기존 개인 세션 재사용, 중앙 로그아웃, 현재 사이트 관리자 로그아웃, 계정 전환, 잘못된 비밀번호, 만료/재사용 티켓, 중앙 장애, 저장소 차단, 원래 메뉴 복귀.
- 비밀번호가 중앙 요청·로그·저장소에 없고, A 방문자 표시가 B 관리자 권한으로 바뀌지 않는지 확인한다.
- 중앙 DB/검증 API와 개인 인증 경로를 준비하고 중앙 Pages → 개인 사이트 → CLI 순으로 맞춘다. 기존 무증명 활성화 요청은 호환 처리로 허용하지 않는다.
- 운영 배포 완료 판정은 로컬 모의 검사와 별도로 실제 배포 URL에서 수행한다.

## 이번 조사에서 실행한 검사

- 개인: `verify-identity.mjs` 실패 (`document` 없음), `verify-visitor-identity-client.mjs` 실패 (`document.querySelector` 없음).
- 중앙: `verify-all.mjs`는 C1~C6 통과 후 C7 API URL 기대값 차이로 중단. C8은 별도 실행해 통과. 합계 8개 중 7개 통과.
- 중앙 검사는 JS handler 및 기존 Edge HTML 중심이며 새 public HTML과 두 사이트 브라우저 왕복을 입증하지 않는다.
- 운영 DB 변경, 배포, 비밀번호 인증은 실행하지 않았다. 기존 미커밋 파일과 `.env` 파일은 변경하지 않았다.

## 이번 범위 밖

- 공통 ID를 댓글·방명록 작성 소유권과 연결하는 DB 개편. 현재 로컬 익명 세션/RLS를 유지하며 별도 후속 작업으로 다룬다.
- 모든 개인 origin의 로컬 세션을 동시에 종료하는 전역 로그아웃.
