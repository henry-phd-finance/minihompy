# 방문 집계 계약 v1

홈 데이터 Step 4의 개인 Supabase 서버 계약. 운영 미적용. 중앙 서버에는 방문 기록을 보내지 않는다. 화면·설정·설치 도구 연결은 Step 5, 운영 배포는 Step 7에서 진행한다.

## 집계 규칙

- 개인 프로젝트마다 같은 브라우저 키는 한국 시간(`Asia/Seoul`) 하루 1회 집계한다. 로그인 여부·회원·소유자 여부를 입력받지 않는다.
- 클라이언트는 암호학적 난수 32바이트를 소문자 64자리 hex `browser_key`로 만들어 사이트별로 보존한다. 로그인·로그아웃으로 키를 바꾸지 않는다. 서로 다른 브라우저/장치, 저장소 삭제 또는 의도적인 키 교체는 별도 방문으로 셀 수 있다. 사람 수를 의미하지 않는다.
- TOTAL은 0에서 시작한다. 기존 설정의 TODAY/TOTAL 숫자를 가져오지 않는다. 날짜가 바뀌면 TODAY는 그 날짜의 집계 또는 0이다.
- Step 5 화면은 실제 보이는 개인 페이지에서만 기록한다. 로그인 전용 페이지·숨은 탭은 제외한다. 로컬 저장소 사용 불가 시 기록을 생략하고 통계 조회만 한다. 방문 실패가 콘텐츠나 인증 흐름을 막아서는 안 된다.

## Edge API

`https://<개인 프로젝트>.supabase.co/functions/v1/visit-counts`

| 요청 | 결과 |
| --- | --- |
| `GET` | `{version:1,date:"YYYY-MM-DD",timezone:"Asia/Seoul",today:0,total:0}` |
| `POST`, JSON `{ "browser_key": "<64자리 소문자 hex>" }` | 위 통계와 `counted: true/false`. 처음 기록만 true |
| `OPTIONS` | 204, CORS 사전 요청 |

GET은 증가·키 생성·정리를 수행하지 않는다. POST는 날짜·증가량·회원 ID 등의 추가 필드를 거부한다. 모든 응답은 `Cache-Control: no-store`이고 허용 Origin을 명시한다. 통계 숫자의 상한은 JavaScript 안전 정수 `9007199254740991`이다. 상한 도달 시 기록 트랜잭션 전체를 취소한다.

JSON 본문은 실제 수신 바이트 기준 256바이트 이하, 전체 본문 읽기 3초 제한이다. 오류는 400(잘못된 입력), 403(다른 Origin), 404(경로), 405(메서드), 408(본문 시간 초과), 413(크기), 415(JSON 필요), 429(요청 제한), 503(미설정/DB 실패/날짜 재시도 실패)로 구분한다. DB 오류나 비밀값은 반환하지 않는다. DB HTTP 요청마다 8초 제한과 리다이렉트 거부를 적용한다.

실패나 응답 유실 후 **같은 키**로 재시도한다. 429는 `Retry-After: 60`; 화면은 이를 존중해야 한다. 자정 사이에 날짜가 바뀌면 Edge가 DB 날짜를 다시 읽어 한 번 재시도한다.

## 저장·권한·원자성

`202609230008_visit_counts.sql`의 `private.visit_total`, `private.visit_days`, `private.visit_keys`에만 저장한다. TOTAL과 날짜별 합계는 유지한다. 중복 키는 Edge에서 `HMAC-SHA256(secret, JSON.stringify([개인 Supabase URL, DB 날짜, browser_key]))`로 계산한다. 원본 브라우저 키·IP·회원 ID를 테이블에 저장하거나 애플리케이션 로그에 출력하지 않는다. 플랫폼 자체의 요청 로그 보관 정책은 이 계약의 데이터 정리와 별개다.

브라우저 역할 `anon`/`authenticated`와 `service_role`의 테이블 직접 접근을 차단한다. `public.visit_stats()`와 `public.visit_record(p_day,p_digest)`만 service_role로 실행한다. 함수는 고정된 빈 search_path와 SECURITY DEFINER를 사용한다. 시각을 주입하는 private 검사 함수는 외부 역할로 실행할 수 없다. 공개 RPC는 DB 시각을 사용한다.

기록 함수는 사이트의 단일 집계 행을 `FOR UPDATE`로 잠근 뒤 중복 키 삽입·일별/전체 증가를 같은 트랜잭션에서 수행한다. `(day,digest)` 기본 키가 중복을 추가로 차단한다. 같은 키의 동시 요청, 응답 유실 후 재시도는 한 번만 증가하며 오류는 부분 증가를 남기지 않는다. 일자는 기록 RPC 실행 시 DB 시각으로 판정한다.

## 제한과 정리

DB 시각의 고정된 분 단위로 사이트 전체 유효 기록 요청 600회, 새로운 중복 키 120개, 기존 키별 요청 60회까지 허용한다. 한도를 넘으면 429이며 방문 수는 늘리지 않는다. 재요청도 사이트 요청 한도를 소모한다. GET은 이 기록 한도를 소모하지 않는다.

그날 최초의 유효 기록 요청에서 오늘보다 3일 이상 오래된 중복 키를 삭제한다. 오늘과 이전 2일 키만 남긴다. 조회는 정리하지 않으므로 방문이 없는 사이트의 오래된 키는 다음 기록 요청까지 남아 있다. 일별 합계와 TOTAL은 삭제하지 않는다. 중앙 회원·기존 게시물·설정 데이터에는 정리를 적용하지 않는다.

Origin은 브라우저 CORS 제한이며 인증이나 부정 집계 방지가 아니다. Origin 없는 외부 요청은 허용되며 Origin을 위조하거나 키를 바꾸는 요청을 완전히 막지 못한다. 사이트 한도는 급격한 증가를 제한하지만 악의적인 요청이 정상 방문의 기록 한도를 소진할 수 있다. GET 트래픽이나 분산 서비스 거부 방어는 이 DB 제한이 보장하지 않는다.

## 비밀값과 설치 인계

필수 Edge 환경은 기존 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, 정확한 HTTPS origin인 `MINIHOMPY_SITE_ORIGIN`, 새 `MINIHOMPY_VISIT_SECRET`이다. Origin에는 경로나 끝 슬래시를 넣지 않는다. Step 5 설치 도구는 프로젝트별로 암호학적 난수 **최소 32바이트**를 hex/base64로 인코딩하여 secret을 최초 한 번 생성하고 Supabase Edge Secrets에 저장해야 한다. 프런트 설정·저장소·출력 로그에는 넣지 않는다. 업그레이드마다 재생성하지 않는다. API는 최소 32문자 유효성만 검사하므로 실제 엔트로피는 생성 과정에서 보장해야 한다.

설치 순서는 SQL 적용 → 최초 secret과 origin 준비 → `visit-counts` 배포(`verify_jwt=false`) → 조회/중복 기록 검증 → 화면 활성화다. 이 단계에서는 로컬 함수 설정만 추가했으며 설치 자동화·운영 secret 생성·배포는 하지 않았다.

같은 날 secret을 바꾸면 동일 브라우저의 HMAC이 달라져 중복 집계될 수 있다. 정상 교체는 기록을 일시 중지하고 기존 실행을 종료한 뒤 키를 교체하고, 다음 한국 날짜가 시작된 후 새 secret의 모든 실행 환경으로 기록을 재개한다. 구/신 secret 인스턴스가 동시에 기록하게 두지 않는다. 날짜 도중 긴급 교체나 롤백은 그날 중복 가능성을 기록해야 한다. 기존 일별 합계와 TOTAL은 보존하며 활성 날짜의 중복 키를 임의로 지우지 않는다.

## Step 5 화면·설치 연결

`home-data-config.js`의 기본값은 비활성이다. `setup/setup.mjs home-data`의 SQL/secret/함수/공개 조회 점검이 성공하면 개인 Supabase URL과 정확한 홈페이지에 묶어 활성화한다. 새 설치와 기존 설치 모두 같은 명령을 사용한다. [설치 안내](../setup/README.md#홈-데이터와-방문-통계-설치업그레이드).

`visit-counts.js`는 공통 TODAY/TOTAL을 관리하므로 홈 이외의 메뉴·직접 글 주소에서도 동작한다. 기존 설정의 `home.today`/`home.total`은 구버전 DB 검증·저장 호환을 위해 보존하지만 표시하거나 방문 집계에 합산하지 않는다. 설정 화면에는 자동 집계 안내만 표시한다.

브라우저 키는 개인 Supabase URL+홈페이지를 포함한 localStorage 이름으로 저장한다. Web Locks로 처음 두 탭이 동시에 열릴 때의 키 생성을 직렬화한다. 저장소나 Web Locks가 없으면 기록을 생략하고 GET으로 조회하며 ‘조회만’을 표시한다. 로그인/계정/메뉴 전환은 키를 바꾸지 않는다. 로그인 전용 문서나 `login_intent` 진입에서는 기록하지 않는다.

표시된 문서에서 최초 로드·포커스/탭 복귀·최대 60초 또는 한국 자정에 갱신한다. 날짜와 실제 중복 여부는 항상 서버가 결정한다. 숨김/pagehide에서는 요청·예약을 취소하며 늦은 응답은 버린다. 기록 요청은 같은 키로 재시도하므로 성공 응답 유실에도 중복 증가하지 않는다. 초기 두 탭의 정확한 집계는 서버의 중복 방지에 맡긴다. 클라이언트의 1초 최소 요청 간격과 429 Retry-After 대기를 적용한다.

진행 중·실패·미준비 상태에서는 숫자 대신 `—`를 표시한다. 실패 시 통계 전용 키보드 접근 가능 재시도 버튼을 제공하며 글/인증 흐름에는 개입하지 않는다. 전체 요청은 10초 후 중단한다. 저장소 접근 실패 외 네트워크/서버 오류를 정상 0으로 바꾸지 않는다. 큰 숫자는 헤더 폭 안에서 표시하고 전체 값과 한국 날짜를 title로 제공한다.
