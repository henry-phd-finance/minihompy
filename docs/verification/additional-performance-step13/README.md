## 성능 수치와 한계

1280×900, Step 1과 같은 측정 도구/메뉴 순서/재진입 2회. HTTP 캐시는 route로 비활성화했고 앱·서버의 워밍 효과는 유지한다. A 검증 뒤 B를 배포했으므로 사이트별 실행 순서는 다르다. 별도의 성능 브라우저를 동시에 실행하지 않았다. 배포 파일 해시 확인은 일부 A 최초 측정 시간과 겹쳤다. CPU·요청별 세부 기록은 JSON에 있으며 1회 운영 표본을 통계적 개선으로 일반화하지 않는다.

확인된 개선은 **중복 요청·초기 편집기 전송·사진 바이트 감소와 초기 식별 안정화**다. 전체 대기 시간 개선을 선언하지 않는다.

- A 주인 첫 문서의 수집된 응답 body 합계: Step 1 **1,049,752 → 936,373B**, 약 113KB 감소. 초기 Quill 요청 2 → 0회. 중앙 왕복 전후의 문서 로딩도 포함한 값이며 사이트 전체 파일 크기가 아니다.
- B에서 A 방문: 첫 관계 health/state **2/2 → 1/1회**. 창 복귀 burst 전체 요청 **13 → 10회**, health/state **2/2 → 0/1회**. 해당 burst 요약은 **1,517 → 1,993ms**로 오히려 늦었다.
- A 사진은 작은 원본 1장뿐이다. 새 선택 metadata 요청 1회가 추가되고 권한 재검사도 유지되어, 비회원 첫 사진 **1,708 → 1,840ms**, 주인 **1,771 → 2,336ms**. 원본 전송량은 줄었지만 이 운영 조건에서 표시 시간은 개선되지 않았다. 큰 이미지의 이득은 Step 12의 바이트 지연 fixture와 구분한다.
- A 주인 첫 편집 **44 → 227ms**. 초기에서 첫 편집 시점으로 코드 다운로드를 옮긴 의도된 비용이다. B의 사진 목록은 비어 있어 이미지 표시 개선을 판정할 수 없다.
- Step 1 B 주인/A에서 B 방문의 실패·명시적 재확인 표본은 이번 정상 최초 문서의 비교 분모로 쓰지 않았다.
- raw network 수집 중 사진 응답 일부는 `pendingAtEnd`/바이트 미확정으로 남는다. 그래서 사진 다운로드 바이트 개선은 불완전한 `request.sizes()` 합계가 아니라 **별도 실제 API body/Storage 해시 검사**의 20,038/4,798B로 판정했다. 운영 첫 페이지에 댓글 회원 링크 대상이 없어 작성자 링크 시간 개선은 Step 12 fixture 근거를 유지한다.

작은 사진에서도 선택 메타데이터 왕복이 늘지 않도록 만드는 것은 후속 성능 과제로 남긴다.
