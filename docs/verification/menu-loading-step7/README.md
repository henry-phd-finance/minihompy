# 메뉴 로딩 개선 Step 7 — 통합 회귀와 성능 비교

완료: 2026-09-27. Step 1~6 완료 확인 후 진행했다. 로컬 fixture·임시 PostgreSQL·정적 artifact 검증이며 운영 A/B·중앙에 접속하거나 배포하지 않았다. Step 8은 미착수다.

## 결과

최종 선정 회귀 28개 스크립트 범위가 통과했다. 최초 실행 실패와 수정/대체 범위를 `regression/results.json`, 원본 로그, `final-results.json`에 함께 보존했다. 모든 오래된 선택적 보조 테스트가 통과했다는 뜻은 아니다.

최종 성능 측정은 비회원/주인/일촌/비일촌/빈 목록 × 다이어리/사진첩 × 최초/재진입으로 각 20회, 신규 capability와 구버전 호환 모드 총 40회다. 네트워크 지연은 Step 1과 동일하다: Auth 20ms, 폴더 40ms, health 100ms, 달력 250ms, 목록/재검증 100ms, 빠른 사진 80ms, 느린 사진 600ms. 권한 응답은 대역이며 댓글은 stub이다. 실서버 권한 정확성은 별도 SQL/API 통합 검사로 검증했다.

재진입 비회원 다이어리는 본문 196ms·요청 3회, 사진첩은 본문 196ms·첫 사진 412ms·전체 946ms·요청 6회였다. 모든 사진 측정에서 첫 사진과 전체 완료 사이 300ms 이상의 차이를 확인했고, 최종 사진 수까지 검사했다. 로딩 문구만 일찍 숨긴 결과로 계산하지 않았다.

## 단계별 효과와 이번 보완

- Step 2: 성공한 health를 공유/재사용한다. 최종 측정은 첫 다이어리에서 health 1회, 같은 유효 수명 안의 다음 메뉴/재진입은 추가 health 없이 진행했다. 만료·실패·취소 검사는 별도 readiness 11그룹으로 통과했다.
- Step 3: 주인 초기 로그인 검증은 유지하고, 동일 세션 메뉴 읽기의 추가 Auth user/admin RPC는 최종 40개 표본 전체에서 0회다. 기존 Step 3 on/off 기록과 함께 최초 확인·갱신·다른 탭의 세션 이벤트·권한 거절·늦은 응답을 회귀 검증했다.
- Step 4: 최신 날짜/글을 목록 1회에 얻고 달력을 독립 조회한다. 측정기는 본문과 달력 완료를 분리해 기록하고 달력까지 끝난 뒤 요청 기록을 닫도록 개선했다. 최신 글·직접 주소·날짜 선택·작성은 실제 UI/SQL 검사로 확인했다.
- Step 5: 사진이 있는 페이지는 목록 1회 후 ID/revision 경량 검사, 빈 페이지는 목록 1회만 수행한다(표의 빈 사진첩 요청 2회는 폴더 1 + 목록 1). SQL/API의 숨김/삭제/이미지 변경·서비스 전용 권한을 유지한다.
- Step 6: 첫 본문 → 빠른 사진 → 느린 사진 순서가 수치와 실제 DOM/디코딩 조건으로 확인된다. 점진 표시로 완료 시점마다 최신 권한을 확인하므로 사진 2/4장 fixture에서는 최종 검사 2회다. Step 4의 마지막 검사 1회보다 1회 늘지만, 최초 Step 1 대비 전체 요청은 줄고 경량 응답은 본문/건수를 재전송하지 않는다.
- 이번 Step 7에서 거의 동시에 준비된 사진이 별도 검사로 갈라지는 현상을 발견했다. `views/photos.js`의 배치 대기를 0 → 16ms로 변경했다. 4장 fixture의 최종 검사 4 → 2회, 전체 요청 10 → 8회다. 파일 준비를 모으는 시간만 16ms이며, 권한 문맥은 모은 후 새로 발급한다. 재검증 진행 중 도착한 사진은 여전히 다음 검사를 받는다. 조정 전 `metrics-legacy/`와 최종 동일 호환 모드 `metrics-legacy-final/`을 보존했다. 조정 뒤 점진 표시 16시나리오·실제 사진 UI/SQL 12시나리오를 재검증했다.

## 회귀 범위

- 준비 상태 캐시, 주인 인증 캐시와 실제 모듈 통합, 회원 runtime/자동 갱신·읽기 401 재시도, 다른 탭 변경 및 늦은 응답 무효화.
- 최신 다이어리, 경량 사진 검사, 중앙+개인 권한 API, 일촌 댓글/요약, 날짜 필터, 사진 클라이언트 및 독립 PostgreSQL 사진/Storage 경합.
- 현재 자동 회원 확인 브라우저를 포함한 댓글 작성·방명록 API/SQL, 홈 요약, 직접 글 주소, 다이어리 작성/달력/충돌, 사진첩 편집/업로드/삭제/댓글, 업로드 중 메뉴 이탈.
- PC/모바일의 느린 사진·개별 오류·순서·재시도·전체 접근 차단·Blob 정리. 1280/375px 캡처는 `regression/verify-photo-progressive/`, `progressive-final/`, `photos-final/` 등에 있다.
- 설치 migration 이력/중단 후 재시도·호환, 새로 빌드한 Pages artifact 구성/해시, 실제 성능 변경 파일과 artifact의 바이트 일치.

`evidence-audit.txt`는 40개 최종 표본의 요청 완료/오류 없음·주인 추가 인증 없음·사진 전체 완료·최대 2개 글 검사 2회, 기록에 요청 본문/전체 URL이 없음, artifact 최신성, 인식 가능한 비공개 토큰 패턴 부재를 확인한다. 모든 형태의 비밀값 부재를 수학적으로 보장하는 스캔은 아니다. 환경 파일/백엔드/검증 로그는 artifact에 포함되지 않으며 기존 인증용 세션 저장소 설계를 변경하지 않았다.

## 테스트 수정 및 남은 구형 보조 테스트

- 홈 테스트가 이전 `<dd>`를 찾고 주인 세션 대역에 user ID/context ID를 제공하지 않았다. 현재 `.home-count-numbers`와 인증 계약으로 fixture를 보완한 뒤 8시나리오 통과(`home-final.log`). 제품의 홈/인증 코드는 변경하지 않았다.
- 직접 주소 테스트에 현재 context의 verify/assert/friendsReady 대역이 빠져 있어 보완했다. 네 메뉴·뒤로 가기·저장 중 이동·삭제/숨긴 대상 PC/모바일 10시나리오 통과(`verify-post-routes-ui-rerun.log`).
- 선택적 `scripts/helpers/guestbook-browser.mjs`는 이미 제거된 회원 확인 버튼을 요구한다. 이전 Step 3에도 기록한 구형 보조 테스트이며 이번에도 통과 처리하지 않았다(`guestbook-obsolete-helper.log`). 방명록 API/SQL 9그룹은 브라우저 옵션을 끄고 통과했고(`guestbook-db.log`), 현재 자동 로그인/작성 UI는 `verify-member-comments`의 최신 자동 세션 브라우저로 검증했다. 재현 runner에서 해당 방명록 스크립트만 이 선택적 구형 helper를 제외했다.

## 재현

`PLAYWRIGHT_PATH`, `CHROMIUM_PATH`를 지정하고 `node scripts/verify-menu-loading-regression.mjs`로 선정 회귀와 새 artifact 빌드를 실행한다. `scripts/measure-menu-loading-fixture.mjs <playwright/index.mjs>`는 기본 신규 capability, `FIXTURE_CAPABILITIES=legacy`는 구버전 호환 모드다. 각 측정의 `VERIFICATION_DIR`을 분리한다. `node scripts/verify-menu-loading-evidence.mjs`로 최종 측정/배포물 기록을 감사한다. 측정은 다른 테스트가 실행되지 않을 때 순차 실행했다.

소스 해시는 `source-hashes.json`, 최초 실행은 `regression.log`/`regression/results.json`, 재검증까지 합친 최종 색인은 `final-results.json`에 있다. JS 문법 검사와 git diff --check도 통과했다. 기존 미커밋 작업을 보존했고 커밋·운영 배포는 하지 않았다.
