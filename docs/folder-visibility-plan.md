## 현재 구현과 보완 지점

- 게시판·사진첩·다이어리의 폴더 테이블과 관리자 쓰기 권한, 글 편집 시 폴더 선택은 있다. 폴더 관리 UI와 동시 변경을 고려한 이동·삭제 절차가 없다. 글이 남은 폴더는 외래키의 `ON DELETE RESTRICT`로 삭제가 막힌다.
- 게시판·사진첩은 폴더/구분선 구조이고 다이어리는 폴더만 있다. 이번에 계층형 폴더로 바꾸지 않는다.
- 일반 게시물은 현재 공개 읽기이며 공개범위 필드가 없다. 방명록에는 별도의 비밀글 정책이 있다.
- `photos-repository.js`는 공개 버킷 `minihompy-photos`의 URL을 사용하고 업로드 캐시 수명도 길다. 글의 RLS만 바꿔서는 사진을 보호할 수 없다.
- 직접 테이블 조회뿐 아니라 `member-writing`의 회원 댓글 처리, 홈 요약, 글 위치 RPC, 다이어리 달력까지 접근 범위를 맞춰야 한다. 특히 서비스 권한으로 실행하는 댓글 처리와 `security definer` 홈 요약은 명시적인 필터가 필요하다.
- 현재 조회 repository는 방문자 client를 사용하는 경로가 있다. 주인의 비공개 조회에는 해당 개인 사이트의 관리자 인증을 전달하고 로그아웃 시 응답·캐시를 폐기해야 한다.

## 실행 기본 정책

Step 1에서 아래 기본값과 [상세 계약](folder-visibility-contract.md)을 확정했다. 사용자가 변경하면 해당 Step의 범위와 검증 기준에 반영한다.

- 폴더는 분류 수단이다. 폴더별 공개범위·하위 폴더·공개범위 상속은 이번 범위가 아니다. 폴더 이름은 방문자에게도 보이며 비공개 내용으로 취급하지 않는다. 게시물·댓글 건수는 조회 가능한 내용만 센다.
- 각 메뉴에서 마지막 실제 폴더 하나는 유지한다. 기존 폴더가 없는 설치 상태는 자동으로 콘텐츠를 변경하지 않고 첫 폴더 생성으로 복구할 수 있게 한다. 게시판·사진첩의 기존 구분선은 보존하고 관리하며 다이어리에 새 구분선 기능은 추가하지 않는다.
- 빈 폴더는 삭제할 수 있다. 글이 있는 폴더는 같은 메뉴의 다른 실제 폴더를 선택해 **모든 글을 이동한 뒤 폴더를 삭제하는 단일 트랜잭션**으로 처리한다. 글 일괄 삭제는 제공하지 않는다. 비공개 글도 이동 대상이며 글 ID·댓글·공개범위·작성일은 보존한다.
- 일반 글은 `공개`와 `나만보기` 두 가지다. 기존 글과 새 글 기본값은 공개이며 주인이 양방향으로 변경할 수 있다. 일촌 공개 선택지는 아직 노출하지 않는다.
- 나만보기의 주인은 해당 개인 Supabase에서 검증된 관리자다. 중앙에 표시되는 방문자 ID나 자기 홈 방문이라는 사실만으로 관리자 권한을 부여하지 않는다. A의 관리자 인증으로 B의 비공개 글을 읽을 수 없다.
- 비공개 부모 글의 댓글은 댓글 작성자라도 볼 수 없으며 작성·수정·삭제도 부모 접근 권한을 따른다. 방명록 비밀글의 주인/작성자 조회와 공개→비밀 전환 정책은 그대로 유지한다.
- 홈은 관리자에게도 공개 데이터만 요약한다. 일반 목록·글 주소·달력은 현재 조회자의 권한을 따른다. 숨겨진 글과 없는 글의 외부 응답으로 제목·위치·건수를 구별하지 못하게 한다.
- 보호 대상 사진은 공개 URL에 의존하지 않는다. Step 1에서 비공개 저장소와 요청별 권한 확인 후 이미지 바이트를 반환하는 개인 서버 방식을 확정했다. 브라우저에 Storage 서명 URL을 발급하지 않는다. 공개 글의 사진은 비로그인 방문자도 정상적으로 볼 수 있어야 한다.
- 이미 공개되어 내려받거나 캐시된 사진은 회수할 수 없다. 기존 공개 URL 폐쇄, 신규 URL/경로, 캐시 및 발급 URL의 유효기간을 구분해 전환 보장 범위를 명시한다. 이 제한을 숨기고 과거 복사본까지 비공개 처리됐다고 안내하지 않는다.
- 다른 메뉴로 이동하면 미저장 입력을 폐기하고 같은 화면의 인증 갱신·저장 실패 중에는 유지하는 기존 정책을 지킨다. 화면 배율·중앙 로그인 방식·일촌 관계는 변경하지 않는다.

## Step 1. 권한·폴더·사진 전환 계약 확정

상태: 완료. 선행 네 계획의 운영 완료 기록과 최신 배포 소스 84개 일치를 확인했다. [계약 v1](folder-visibility-contract.md)에 폴더 RPC·경합·권한표·전체 읽기 경로·인증별 캐시 폐기·사진 proxy 및 기존 파일 전환을 확정했다. 후보 사진 SQL/실제 로컬 HTTP 최소 실증 11개, 기존 작성 기반 10개·회원 댓글 통합 9개 그룹 통과. [검증 범위와 근거](verification/folder-visibility-step1/README.md). 운영 코드·DB·Storage는 변경하지 않았다.

- 선행 계획의 완료 문서·구현·검증 근거를 확인한다. 미완료가 있으면 바로 중단한다.
- 폴더 CRUD/정렬/글 이동, 충돌 처리, 마지막 폴더 규칙과 API 계약을 정한다. 기존 글 편집의 폴더 이동을 재사용할 범위도 정한다.
- 비로그인·비회원 작성자·중앙 회원·개인 관리자별 읽기/쓰기 권한표와 모든 조회 경로를 작성한다. 관리자 모드와 방문자 모드 전환 시 client 선택·캐시 폐기 규칙을 정한다.
- 사진의 저장 경로·게시물 연결·임시 업로드·읽기·삭제 정책과 기존 공개 파일 전환 순서를 정한다. 로컬에서 공개/비공개 사진 접근과 만료를 실증한다. 확정 방식은 URL을 발급하지 않으므로 서명 URL 대안의 만료/캐시 잔존 비교와 채택 경로의 인증 만료 차단으로 검증한다. 실제 Storage에서 확인해야 할 사항은 Step 10에 명시한다.
- 폴더 이동 시 revision/updated_at, 목록 정렬·직접 주소의 동작과 경쟁 상황을 확정한다.

완료 기준: `docs/folder-visibility-contract.md`에 결정 사항·접근 경로 목록·권한표·사진 전환 방식을 기록하고 실증 근거를 남긴다. 사진 보호 방식을 결정하지 못하면 미완료로 두고 다음 Step을 시작하지 않는다.

## Step 2. 폴더 관리 서버 기능

상태: 완료. Step 1 근거·소스 110개 일치를 확인했다. 개인 migration `202609240001_content_folders.sql`에 관리자 폴더 RPC, 직접 DML 차단, 메뉴별 잠금/구조 revision, 재시도 기록과 이동 후 원자적 삭제를 구현했다. SQL 11개·독립 PostgreSQL 연결 경합 15개 그룹 및 새 migration 적용 상태의 기존 댓글/홈/주소 회귀 통과. [Step 2 검증 기록](verification/folder-visibility-step2/README.md). 운영 미적용, 화면은 Step 3 범위다.

- 세 메뉴의 폴더 생성·이름 변경·정렬·빈 폴더 삭제 및 구분선 관리를 구현한다.
- 비어 있지 않은 폴더의 이동 후 삭제를 원자적으로 처리한다. 다른 메뉴·자기 자신·구분선으로의 이동과 마지막 폴더 삭제를 거절한다.
- 개별 글 이동 경로도 동일한 무결성 규칙을 따른다. 직접 테이블 쓰기로 RPC의 규칙을 우회하지 못하도록 권한·제약을 조정한다.
- 동시 생성/정렬/삭제/글 저장과 재시도를 처리한다. 기존 데이터와 폴더 ID는 유지한다.

완료 기준: 실제 SQL 권한 검사와 독립 DB 연결 경합 검사로 관리자만 변경 가능하고 글 유실·부분 이동·마지막 폴더 동시 삭제가 없음을 확인한다.

## Step 3. 세 메뉴의 폴더 관리 화면

상태: 완료. Step 2 근거·소스 113개 일치를 확인했다. 공통 관리자 repository/관리 창과 세 메뉴 진입점을 연결하고, 폴더 변경 후 선택·글 위치·편집 목록 갱신 및 충돌/응답 유실/인증·메뉴 이탈 처리를 구현했다. 실제 화면·repository·SQL 통합 20개 그룹(1280px/375px), 기존 세 메뉴 작성 3개 스위트 및 Pages 검사 통과. [Step 3 검증 기록](verification/folder-visibility-step3/README.md). 운영 미적용, Step 4 미착수.

- 주인에게 폴더 관리 진입점을 제공한다. 공통 관리 UI와 메뉴별 adapter로 생성·이름 변경·위/아래 이동·삭제를 연결한다. 드래그 전용 조작은 피한다.
- 글이 있는 폴더 삭제 시 이동 대상과 결과를 확인하게 한다. 관리자가 보는 대상 건수에는 비공개 글도 포함한다.
- 삭제·이동 뒤 선택 폴더·목록·편집 선택지·글 주소를 갱신하고 충돌은 재조회로 복구한다.
- 저장 중 중복 요청, 로그아웃, 메뉴 이탈 후 늦은 응답을 처리한다.

완료 기준: 세 메뉴에서 생성부터 이동 후 삭제까지 실제 repository/API로 검증한다. 방문자에게 관리 UI가 없고 키보드·좁은 화면에서도 조작 가능함을 확인한다.

## Step 4. 일반 게시물과 댓글의 서버 공개범위

상태: 완료. Step 3 기록·소스 116개 일치를 확인했다. migration `202609240002_content_visibility.sql`로 일반 글 visibility/RLS, 관리자 변경·재시도 RPC, 로컬/회원 댓글 부모 검사와 사진 media-ready 차단을 구현했다. SQL 10개·PostgreSQL 경합 14개·회원 댓글 12개·방명록 9개 및 기존 폴더 11개 그룹 통과. [Step 4 검증 기록](verification/folder-visibility-step4/README.md). 운영 미적용. 홈 집계는 Step 5에서 연결하므로 중간 배포하지 않는다.

- 일반 게시물에 공개범위와 기본값을 추가하고 기존 글은 공개로 보존한다. 변경 권한과 동시 수정/retry 계약을 적용한다.
- 목록·상세·count의 RLS와 일반 댓글 부모 접근 검사를 연결한다.
- 서비스 권한을 사용하는 회원 댓글 RPC/handler에도 부모 공개범위 검사를 적용한다. 재시도 결과 조회도 현재 권한을 재검증한다.
- 공개범위 변경과 댓글 작성/수정이 동시에 일어나도 권한을 우회하지 못하도록 처리한다.
- 아직 사진 파일 전환 전이므로 사이트별 media-ready 전에는 사진 private 저장을 서버에서 거절한다. 이 Step만으로 사진첩 비공개 기능을 활성화하거나 운영 배포하지 않는다.

완료 기준: 실제 SQL 및 회원 handler로 역할별 글·댓글 접근과 위조/직접 요청을 검사한다. 기존 방명록 비밀글·익명/회원 소유권과 작성 제한이 유지됨을 확인한다.

## Step 5. 홈 요약·달력·글 주소의 공개범위 연결

상태: 완료. Step 4 기록·소스 119개 일치를 확인했다. migration `202609240003_visibility_summary.sql`에 일반 글의 명시적 공개 필터를 추가했다. 기존 invoker 글 위치·달력·목록 RLS를 혼합 데이터로 검증했으며, 실제 화면/SQL 직접 주소·뒤로가기·새로고침 6개 그룹과 SQL 8개 그룹, 기존 홈 요약·글 위치/방명록·방문 집계 회귀를 통과했다. [Step 5 검증 기록](verification/folder-visibility-step5/README.md). 운영 미적용. 관리자 reader UI는 Step 7~8 범위다.

- 홈 요약의 최근 글·메뉴 건수·새 댓글을 명시적으로 공개 글만 집계하도록 변경한다.
- 다이어리 달력 날짜와 목록 count, 글 위치·페이지 계산은 호출자의 읽기 권한을 따른다.
- 비공개 전환/폴더 이동/삭제 직후 직접 주소·뒤로가기·새로고침 시 제한 정보를 노출하지 않도록 처리한다.
- 방문 집계 정책과 기존 방명록 위치 조회는 유지한다.

완료 기준: 공개/비공개 혼합 데이터로 홈 요약, 날짜, 페이지 경계, 직접 주소를 실제 DB에서 검증한다. 관리자용 목록과 공개 홈 요약의 차이를 확인한다.

## Step 6. 사진 파일 접근 제어와 전환 도구

상태: 완료. - 기존 공개 URL 차단과 캐시/URL 만료의 한계를 문서화한다. 복구 때 비공개 파일을 다시 공개하지 않는 절차를 마련한다.

완료 기준: 로컬 저장소 연동 검증으로 업로드·읽기·전환·중간 실패 복구를 확인한다. 모의 Storage로만 확인한 항목은 구분하고 실제 Supabase Storage 검증을 Step 10의 필수 조건으로 남긴다. 운영 파일은 아직 변경하지 않는다.

## Step 10. A/B 운영 적용과 실제 계정 검증

상태: 완료. Step 9 기록·소스 151개 일치를 확인하고 A→B 순서로 DB/함수/Pages·사진 보호 전환을 적용했다. 실제 계정·모바일/데스크톱·A→B 회원 댓글/비공개 접근 차단·6 MiB/동시 읽기·로그아웃·응답 유실 복구와 테스트 정리를 확인했다. 기존 데이터·설정·파일 SHA-256 보존 및 제공 runtime 50개씩 대조 완료. 실제 Supabase safeupdate에 맞춘 migration 005와 초기 관리자 확인/회원 증명 교환 경합 보완도 검증·배포했다. [Step 10 운영 기록](verification/folder-visibility-step10/README.md). 일촌 공개는 후속 범위다.

- A/B의 권한·현 배포·DB/Storage 상태를 확인하고 데이터와 파일의 비공개 백업을 만든다. 필요한 접근 권한이 없다면 적용을 중단하고 부족한 항목을 알린다.
- 실제 Supabase에서 임시 데이터로 Storage 접근 계약을 먼저 검증한다. 배포 절차에 따라 A를 적용·검증한 뒤 B를 진행하며 운영 데이터 전환도 실행한다.
- 실제 계정으로 폴더 변경·이동 후 삭제·공개범위 변경·사진 표시·댓글·홈/달력/주소를 확인한다. 비로그인과 A→B 방문에서 비공개 글/사진/건수가 유출되지 않고 옛 공개 파일 경로가 더 이상 원본을 제공하지 않는지 확인한다. 이미 보유한 캐시의 회수 불가능성은 별도로 기록한다.
- 테스트 콘텐츠를 정리하고 기존 콘텐츠·댓글·폴더 연결·설정·회원 소유권과 사진 무결성을 비교한다. Pages 및 함수/DB 배포 버전을 기록한다.
- 백로그의 완료된 체크박스만 갱신한다. 일촌 공개는 계속 미완료로 남기고 백로그 5번 이후로 연결한다.

완료 기준: A/B 운영 검증·보존 근거·테스트 정리·배포 기록까지 남겨야 완료다. 코드만 작성하거나 로컬 검증만 통과한 상태는 Step 10 완료가 아니다.

## 실행 및 기록 규칙

- 요청받은 Step 전에 이전 Step의 완료 기록·구현·검증 근거를 확인한다. 미완료라면 즉시 중단하고 부족한 항목을 알린다. Step 1은 명시한 선행 계획에 같은 규칙을 적용한다.
- 한 번 요청으로 해당 Step만 실행한다. 구현·문서·검증을 마쳐야 완료로 기록하고 다음 Step은 자동 실행하지 않는다.
- 검증 기록은 `docs/verification/folder-visibility-stepN/`에 남긴다. 사용한 소스 버전/해시, 검사 결과와 남은 제약을 기록하며 계정 비밀값·비공개 콘텐츠는 저장소에 넣지 않는다.
- Step 1~9는 로컬 구현·검증·배포 준비다. 운영 변경은 Step 10에서 수행한다. 중간 Step의 일부 보안 기능만 배포하지 않는다.
- 기존 미커밋 작업은 유지하고 관련 없는 파일을 변경하지 않는다. 이후 일촌 공개는 검증된 관계와 개인 서버 권한을 연결하는 별도 후속 작업이다.
