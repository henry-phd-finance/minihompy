# 홈·회원 조회·사진 전송 추가 성능 개선 계획

작성: 2026-09-27. Step 1~4 완료(2026-09-28), Step 5~13 미착수. 사용자가 요청한 단계만 순서대로 실행한다.

이전 [메뉴 로딩 개선 8단계](menu-loading-performance-plan.md)는 완료된 작업으로 유지한다. 이번 계획은 이후 추가된 인삿말 HISTORY와 일촌평 내역을 포함한 현재 배포본을 출발점으로 삼는다.

## 목표와 범위

1. 우측 일촌 표시와 일촌평에서 중복되는 준비 상태·관계 조회를 공유한다.
2. 로그인/포커스 복귀 등 연속 이벤트로 홈 요약을 반복 취소·재조회하는 일을 줄인다.
3. 댓글·방명록·일촌평의 같은 작성자 공개 프로필 조회를 공유한다.
4. 사진 원본을 유지하면서 화면 표시용 작은 이미지를 만들어 전송량을 줄인다.
5. 주인이 사진 편집을 시작할 때 편집기를 불러와 첫 접속 부담을 줄인다.

현재 판단은 코드 검토에 따른 개선 후보다. 실제 기여도·시간·전송량은 Step 1과 Step 12/13에서 같은 조건으로 측정한다. 앞선 계획에서 이미 개선한 본문 우선 표시·최신 일기 첫 조회·주인 인증 재사용을 다시 구현하지 않는다.

## 실행 규칙

- **이전 Step이 하나라도 미완료이면 즉시 중단한다.** 이전 단계의 구현뿐 아니라 요구된 검증·기록도 확인한다.
- 한 요청에는 해당 Step만 수행한다. 각 Step은 구현/검증/기록을 마친 뒤 완료 상태로 바꾼다. 뒤 단계가 남아 있어도 자신의 로컬 완료 범위는 명확히 표시한다.
- **Step 1~12는 로컬 준비, 운영 변경과 A/B 배포는 Step 13에서만 수행한다.** 기준 측정을 위한 운영 조회는 허용하되 글·프로필·관계·파일을 수정하지 않는다. 방문 통계도 가능한 한 기존 조회 전용 경로를 사용한다.
- 단계 결과는 `docs/verification/additional-performance-stepN/`에 남긴다. 필요한 테스트만 실행하고 한 번 통과한 범위를 이유 없이 반복하지 않는다.
- 해당 단계 변경만 커밋하여 Git 작업 트리를 정리한다. 다른 작업의 변경은 섞지 않는다. Step 1~12에는 main push로 Pages 자동 배포를 일으키지 않는다.
- 설치 SQL은 새 migration으로 추가한다. 적용한 SQL을 수정하지 않는다. 중앙 저장소 변경이 필요하면 `~/minihompy-central`의 대응 변경·검증도 해당 단계 결과에 포함한다.
- 자격 증명, 인증 토큰, 실제 비공개 본문/사진을 Git·Pages·검증 로그에 넣지 않는다.

## 유지할 동작과 기본 정책

- 디자인·메뉴 동작·본문/댓글 표시 순서를 유지한다. 메뉴를 나갈 때 작성 초안은 버린다.
- 공통 회원 세션과 개인 Supabase 주인 세션을 구분한다. 이미 구현한 자동 갱신·같은 주인 세션 재사용을 유지한다.
- 서버는 요청마다 실제 조회/쓰기 권한을 검사한다. 브라우저의 관계 표시, 준비 상태, 공개 프로필 캐시로 일촌 글 읽기나 일촌평 쓰기를 허용하지 않는다.
- 로그아웃·계정 전환·사이트/프로젝트 변경·권한 거절 시 관련 요청/캐시를 무효화한다. 늦은 응답이 다음 사용자 화면에 적용되지 않게 한다.
- 공유 요청을 기다리던 위젯 하나가 사라져도 다른 대기자의 요청은 살아 있어야 한다. 변경 요청·방문 집계 POST·회원 갱신을 일반 조회처럼 합치거나 자동 재전송하지 않는다.
- 재사용은 메모리 안에서 제한한다. 준비 상태 성공 응답은 기존 content health와 같은 30초를 기본값으로 한다. 관계 상태는 우선 **진행 중인 동일 조회만 공유**하고 완료 응답의 장기 캐시는 도입하지 않는다.
- 작성자 공개 프로필은 정상 결과만 최대 30초 메모리 재사용을 기본으로 한다. 비활성/없음/오류는 성공 캐시로 남기지 않는다. 실제 미니홈피 이동 시 등록 상태와 목적지를 다시 확인한다.
- 보호 콘텐츠를 새 권한 확인 전에 이전 캐시로 먼저 보여주지 않는다. 홈 이벤트 묶기는 인증 변경 시의 즉시 화면 정리를 지연시키지 않는다.
- HISTORY는 열 때 조회하는 현재 방식으로 유지한다. 최근 추가 기능을 이유로 첫 홈 화면에 이력 전체를 미리 내려받지 않는다.

### 표시용 사진의 기본안

- 원본과 게시글 본문에 기록된 원본 경로는 유지한다. 표시용 파생 이미지는 원본 asset/게시글에 연결된 별도 보호 파일이다.
- 우선 JPEG/PNG/WebP 정지 사진에 한 종류의 표시용 이미지를 사용한다. 긴 변 최대 1200px, 확대 없음, WebP 품질 0.82를 후보 기본값으로 삼는다. 실제 렌더링 폭·배율·품질/바이트 비교를 Step 1에서 확인하여 수치를 확정한다.
- GIF는 원본 재생을 유지한다. 그 밖에 애니메이션·투명도·회전 방향을 보존할 수 없는 입력은 원본 사용으로 처리한다. 애니메이션을 조용히 정지 이미지로 바꾸지 않는다.
- 원본보다 작아지지 않는 파일은 파생 파일을 만들지 않는다. 변환 메모리/최대 픽셀 제한과 실패 시 원본 사용을 정의한다.
- 신규 업로드는 주인 브라우저에서 변환하는 방식을 기본으로 한다. 기존 파일은 Step 10의 별도 운영 도구로 추가 생성한다. 별도 유료 이미지 변환 서비스 도입은 포함하지 않는다.
- 서버가 관리하는 경로·크기·형식·해시와 준비 완료 상태로만 표시용 파일을 선택한다. 공개 버킷·공개/서명 URL로 보호 파일을 우회 제공하지 않는다.
- 파생본에도 원본과 같은 공개/일촌/나만보기 권한과 다운로드 전후 검사, revision/파일 연결 재확인을 적용한다. 권한 실패에는 원본으로 재시도하지 않는다. 지원하지 않는 구 서버·파생본 미생성/변환 실패의 호환 경로만 원본을 사용한다.

## Step 1 — 현재 기준 측정과 세부 계약 확정

상태: 완료 (2026-09-28). 선행 단계 없음.

결과: [기준 측정·실패 및 회귀 기록](verification/additional-performance-step1/README.md), [세부 계약·단계별 검증 목록](additional-performance-contract.md). A/B 역할별 조회와 로컬 fixture를 측정했다. B 계정 초기 식별 실패 및 명시적 재확인 후 복구는 정상 latency와 분리해 기록했다. 운영/runtime 변경·배포 없이 로컬 도구/문서만 준비했다.

- 현재 A/B 배포 버전과 로컬 차이, 기존 성능 검증·권한 계약을 확인한다.
- 첫 방문/메뉴 재진입/창 복귀를 구분하고 비회원·주인·다른 홈의 회원에서 홈 요약, 관계 표시, 일촌평 입력 가능, 댓글 작성자 링크, 첫 사진/전체 사진, 첫 편집 가능 시간을 측정한다.
- 요청 수·중복 대상·취소 후 재시작·대기 순서·응답 바이트·정적 파일 다운로드/실행을 구분한다. 최초/반복 캐시 조건, 실패와 느린 첫 요청도 기록한다. 과거 다른 조건의 측정값을 이번 개선율의 분모로 쓰지 않는다.
- 동시 위젯·연속 이벤트·여러 작성자·작은/큰/여러 사진·빈 목록의 고정 지연 fixture와 계측 도구를 준비한다. 운영 데이터가 없는 사례는 격리 fixture로 검사한다.
- 사진 변환 위치/크기/품질/지원 형식, DB 연결 구조, API capability/요청 필드와 중앙 사진 확인에 묶이는 값, 업로드/삭제/복구 순서를 계약 문서에 확정한다. 이전 클라이언트와 새 서버, 새 클라이언트와 이전 서버의 동작을 명시한다. 확정값·API 필드는 [Step 1 계약](additional-performance-contract.md)을 따른다.

완료 기준: 재실행 가능한 기준 측정과 요청 목록, `docs/additional-performance-contract.md`, 단계별 검증 목록이 있다. 이 단계에서 화면/권한/저장 동작이나 운영 환경은 변경하지 않는다.

## Step 2 — 관계 서버 준비 상태 조회 공유

상태: 완료 (2026-09-28). 선행 Step 1 완료 확인.

결과: [Step 2 구현·검증](verification/additional-performance-step2/README.md). 공통 health 요청 공유·성공 응답 30초 재사용·부분 취소·무효화를 구현했다. 동일 조건 초기 health 3→1회, 30초 이내 복귀 2→0회. 실제 관계/쓰기 권한 검사는 유지하며 운영 배포는 하지 않았다.

- `member-relationships-repository.js`와 `friend-reviews-repository.js`의 동일 `/relationships/health` 조회를 공통화한다.
- 같은 프로젝트/사이트의 진행 중 조회를 공유하고 정상 준비 상태만 최대 30초 재사용한다. 각 소비자는 자신에게 필요한 capability를 따로 확인한다.
- 설정 변경·배포 capability 불일치·관련 오류·명시적 재시도 시 재검사하고, 대기자별 취소를 분리한다. 기존 content health 캐시와 무효화 정책을 맞추되 서로 다른 endpoint를 같은 결과로 취급하지 않는다.

완료 기준: 동시에 관계 UI와 일촌평이 확인할 때 health 요청은 1회. 만료/오류/설정 전환/부분 취소 검증 통과. 관계나 작성 권한 검사 횟수를 임의로 줄이지 않는다.

## Step 3 — 동일한 일촌 관계 조회 공유

상태: 완료 (2026-09-28). 선행 Step 1~2 완료 확인.

결과: [Step 3 구현·검증](verification/additional-performance-step3/README.md). 진행 중 state 공유와 갱신 이벤트 묶기, 세션 준비·변경/취소 경합 방어를 구현했다. 동시 위젯과 창 복귀의 state 2→1회, 변경 이벤트 burst도 1회. 완료 응답/쓰기 권한은 캐시하지 않으며 운영 배포는 하지 않았다.

- 우측 관계 표시와 일촌평에서 같은 방문자·홈 주인 쌍의 `/relationships/state` 진행 중 요청을 공유한다.
- 현재 두 UI가 서로 refresh를 유발하는 경로를 정리하고, 관계 변경 후 갱신 요청도 한 번으로 모은다.
- 요청 키에 사이트·방문자·대상·세션 세대를 포함한다. 관계 신청/수락/끊기/로그아웃과 경합하면 이전 결과를 폐기한다.
- 관계 변경 POST와 일촌평 생성의 중앙 쓰기 허가 검사는 기존대로 유지한다. 실패한 조회가 표시상 일촌으로 남지 않게 한다.

완료 기준: 동일 상태를 요구하는 동시 위젯에서 관계 조회 1회. 타 회원/다른 홈 간 공유 없음, 관계 철회·응답 역전·세션 갱신 회귀 통과.

## Step 4 — 홈 갱신 이벤트 묶기

상태: 완료(2026-09-28). 선행: Step 1~3 완료 확인.

결과: [Step 4 구현·검증](verification/additional-performance-step4/README.md). 홈 갱신 50ms 묶기와 진행 중 조회 공유, 즉시 권한 무효화, 새 성공 응답 이후 동일 DOM 재사용을 구현했다. 창 복귀 summary 3→1회, 취소 2→0회. 자정·숨김·계정 전환·재시도 및 실제 API/SQL 일촌 공개 검증 통과. 운영 배포는 하지 않았다.

- `home-activity.js`의 focus/pageshow/visibility/인증/콘텐츠 이벤트를 구분한다. 같은 상태에서 짧게 연달아 온 갱신 요구를 한 번으로 합친다.
- 동일 조건으로 진행 중인 조회는 이어서 기다린다. 실제 인증·공개범위 변화는 즉시 이전 표시를 정리하고 요청을 교체한다.
- 숨겨진 문서에서 새 조회를 시작하지 않는다. 기존 분 단위 갱신·한국 시간 자정·명시적 다시 시도·메뉴 이탈 취소는 유지한다.
- 필요할 때만 DOM을 다시 그리고, 댓글 초안이나 다른 메뉴를 불필요하게 재마운트하지 않는다. 단순히 이전 보호 데이터를 계속 보여주는 방식으로 빠르게 보이게 하지 않는다.

완료 기준: 동일 상태의 연속 이벤트에서 요약 요청이 1회로 수렴하고 취소/재시작이 감소한다. 계정 전환·쓰기 직후·자정·숨김/복귀에서 최신성 및 보호 화면 정리 검증 통과.

## Step 5 — 작성자 공개 프로필 조회 공유

상태: 미착수. 선행: Step 1~4.

- `author-navigation.js`의 기존 일괄 조회에 진행 중 회원 ID별 요청 공유와 30초 메모리 재사용을 더한다.
- 다른 시점에 렌더링되는 댓글·방명록·일촌평이 같은 회원의 결과를 공유하게 한다. 기존 요청당 50명 제한은 유지한다.
- 프로젝트/중앙 주소 변경, 관련 무효화 이벤트와 직접 재시도는 캐시를 갱신한다. 비활성/오류는 링크를 활성화하지 않는다.
- 캐시된 이름/주소를 표시하더라도 실제 이동 시 최신 등록 상태·URL을 확인한다. 확인 중 중복 클릭, 키보드·새 창 열기 등 링크 동작과 실패 안내를 정의하고 검사한다.

완료 기준: 같은 작성자가 여러 위젯/재렌더에 등장해도 표시용 중복 조회가 감소한다. 정지 회원·주소 변경·만료·실패·메뉴 이탈에서 오래된 링크로 잘못 이동하지 않는다.

## Step 6 — 표시용 사진 DB와 파일 수명주기

상태: 미착수. 선행: Step 1~5.

- 새 migration으로 원본 asset과 표시용 파일의 연결·변환 버전·크기/형식/해시·처리 상태를 기록한다. 기존 글/원본 행/경로를 수정하지 않는다.
- 생성 예약 → 업로드 확인 → 사용 가능 전환을 나누고 중복 실행, 부분 실패, 원본 수정/삭제와의 경합을 처리한다.
- 정리 절차에서 원본과 연결된 파생 파일을 함께 관리한다. 사용 중 파일·다른 글의 파일을 지우지 않고, 실패 후 재시도와 삭제 tombstone 정책을 유지한다.
- 모든 SQL은 기존 권한 경계 안에서 실행한다. 공개 사용자가 파생 경로 목록이나 비공개 메타데이터를 직접 얻지 못하게 한다.

완료 기준: SQL 수명주기·권한·해시 일치·동시 처리·삭제 경합 테스트 통과. 아직 파생본을 화면에 사용하거나 운영 파일을 변환하지 않는다.

## Step 7 — 새 업로드의 표시용 사진 생성

상태: 미착수. 선행: Step 1~6.

- 격리 변환 모듈과 `photo-media` 주인 전용 파생 파일 업로드/완료 경로를 구현하고 신규 사진 작성·수정에 연결한다.
- 원본을 보존하면서 확정한 크기의 파생본을 만든다. 디코딩 실패·픽셀/메모리 제한·방향/투명도/애니메이션·용량 이득 없음을 처리한다.
- 파일 일부 실패/저장 응답 유실/재시도에서 중복 생성이나 잘못된 완료 처리를 막는다. 파생본 생성 실패가 정상 원본까지 잃게 하지 않는다.
- 작업 중 메뉴 이탈·주인 전환 시 변환 결과·업로드·미리보기 URL을 정리한다. 새로운 서버 capability가 없는 경우 기존 원본 업로드로 동작한다.

완료 기준: 신규 업로드의 원본/파생본 보존·품질·실패 복구·취소 검증 통과. 파생본이 만들어져도 다음 읽기 단계 전까지 기존 읽기 동작을 유지한다.

## Step 8 — 표시용 사진의 보호된 서버 읽기

상태: 미착수. 선행: Step 1~7.

- photo-media의 public/owner/member 읽기에서 원본 경로와 허용된 variant 식별자로만 준비된 표시용 파일을 선택한다. 클라이언트 임의 Storage 경로는 받지 않는다.
- 원본 게시글 권한·일촌 관계·현재 revision/파일 연결 검증을 파생본에도 적용한다. 회원 read-context 및 다운로드 전후 검사에 선택한 파일과 변환 버전을 포함한다.
- 개인 member-writing의 사진 확인 응답·photo-media health를 필요한 만큼 확장한다. 중앙 서명/확인 범위 변경이 필요하면 중앙 대응 변경도 이 단계에서 검증한다.
- 원본 사용 조건을 분명히 한다. 미생성·구버전과 권한 거절·무결성 실패를 구분하고 보호 오류에서 원본 우회가 발생하지 않게 한다.

완료 기준: 공개/일촌/나만보기, 관계 철회, 교체/삭제, 잘못된 파일·context 재사용, 구/신 버전 조합 검증 통과. 기존 사진 조회도 유지된다.

## Step 9 — 사진첩의 표시용 사진 사용

상태: 미착수. 선행: Step 1~8.

- photo-media-client와 사진첩에 표시용 파일 선택을 연결한다. 본문 경로와 원본 저장 데이터는 유지한다.
- 기존 본문 우선 표시, 가까운 사진 우선·동시 4개, 개별 오류 재시도, 디코딩 후 최대 2개 글 재검증 묶음을 유지한다.
- 준비된 파생본부터 표시하고 지원하지 않는 서버/파일은 계약에 따라 원본을 사용한다. 작은 이미지를 먼저 표시한 뒤 원본도 무조건 다운로드해 전송량을 늘리지 않는다.
- 사진 비율·방향·투명도·GIF 재생·큰 화면 표시 품질, 메뉴 이탈·로그아웃 시 요청/Blob 정리를 확인한다.

완료 기준: 대표적인 큰 사진 fixture에서 실제 전송 바이트 감소와 첫 사진 시간 개선을 측정한다. 이미지가 이미 작은 경우 불필요한 변환/추가 요청이 없다. 사진 권한과 경합 회귀 통과.

## Step 10 — 기존 사진의 파생본 생성 도구

상태: 미착수. 선행: Step 1~9.

- 기존 원본을 읽어 파생본만 추가하는 도구를 만든다. 대상 프로젝트/원본 해시/게시글 연결을 확인하며 기본 실행은 dry run으로 한다.
- 비공개 journal로 대상·변환 버전·완료/실패를 추적하고 재실행 시 완료 파일을 중복 생성하지 않는다. 다운로드·변환 동시성 및 저장 공간 상한을 둔다.
- 처리 도중 원본이 수정/삭제되면 파생본을 현재 글에 잘못 연결하지 않는다. 미완료 임시 파일 정리와 안전한 중단/재개를 제공한다.
- 원본 삭제·기존 공개범위 변경·본문 경로 교체는 수행하지 않는다. 실제 A/B 실행은 Step 13에서 한다.

완료 기준: 격리 데이터의 변환·중단/재개·중복 실행·삭제/교체 경합·원본 해시 보존 검증 통과. 운영 대상 dry run으로 예상 파일 수/추가 저장량을 기록한다.

## Step 11 — 사진 편집기 지연 로딩

상태: 미착수. 선행: Step 1~10.

- 홈 첫 접속에서 Quill과 사진 편집기 초기화 코드를 내려받거나 실행하지 않는다. 주인이 사진 새 글/수정을 요청할 때 로컬의 고정 버전을 로드한다.
- `photo-editor.js`의 최상위 Quill 의존 초기화를 정리하고 중복 클릭은 같은 로딩 작업을 공유한다. 로드 중/실패·다시 시도 상태를 제공한다.
- 로딩 도중 메뉴 이탈/로그아웃하면 편집기를 늦게 열지 않는다. 정상 로드된 정적 코드만 재사용하고 초안은 메뉴 이탈 시 버린다.
- 새로 들어간 사진 변환 모듈도 필요 시점에 맞춰 로드한다. 공개 사진 본문 표시에 필요한 코드는 남기며 Supabase SDK 전체 지연 로딩은 이번 범위에 넣지 않는다.
- Pages/설치 패키지의 의존성 검사와 전체 JS 파일 해시에 동적 로드 파일도 포함한다.

완료 기준: 일반 방문/홈 조회에 편집기 요청 0회, 첫 편집과 재편집 정상 동작. 초기 전송량·첫 편집 대기를 각각 측정하고 취소/실패/쓰기 회귀 통과.

## Step 12 — 설치 연결·통합 회귀·전후 측정

상태: 미착수. 선행: Step 1~11.

- Step 1에서 관측한 B 계정의 초기 식별 실패(자기 홈 새로고침/상대 홈 첫 방문)를 재현·원인 확인하고, 운영 배포 완료 전에 해결 여부를 명시한다. 재확인으로 복구된 결과를 무버튼 정상 인증으로 계산하지 않는다.

- 신규 install과 기존 업그레이드, 전체 migrations/functions, capability 검사, 사진 파생본 전환/복구 문서를 연결한다. 설치 파일 버전과 manifest를 갱신하고 실제 압축 해제 상태에서 점검한다.
- 변경된 SQL·함수·정적 파일을 배포 목록으로 확정하고 소스 해시를 기록한다. 서버를 먼저 바꾸고 Pages를 뒤따라 바꾸는 호환 순서를 검사한다.
- Step 1과 같은 고정 지연 조건으로 첫 방문·홈 복귀·작성자 표시·사진 다운로드·편집 진입을 비교한다. 요청/바이트/실제 준비 시간을 보고하며 실패를 성공 표본으로 섞지 않는다.
- 신규 공유 요청의 취소/무효화, 기존 회원 세션·관계·댓글/일촌평·인삿말 HISTORY·사진 쓰기/공개범위와 삭제 경합 중 영향받은 범위를 검증한다.
- A/B 운영 데이터·원본·설정 보존 점검과 파생본 사용 비활성화/안전한 화면 복원의 복구 절차를 준비한다. 보호 SQL을 철거하는 롤백은 사용하지 않는다.

완료 기준: 관련 회귀 통과, 변경별 전후 지표와 한계 기록, 신규/기존 설치 재실행 및 패키지 검사 통과. 배포 가능한 하나의 소스 버전과 실행 순서가 고정된다.

## Step 13 — A/B 배포·기존 사진 반영·실측

상태: 미착수. 선행: Step 1~12.

- A 먼저, 성공을 확인한 뒤 B에 적용한다. 사이트별 기존 설정·콘텐츠·원본 파일 해시와 준비 상태를 기록한다.
- 필요한 중앙 변경이 있다면 먼저 적용한 뒤 개인 SQL/함수 → 기존 사진 파생본 생성 → 해당 사이트 설정을 보존한 Pages → 실제 제공 파일 검증/일촌 공개 release 활성화 순으로 진행한다.
- 기존 사진 도구는 Step 10의 검증된 대상·동시성·journal로 실행한다. 원본과 게시글은 보존하고 파생본만 추가한다. 부분 실패는 기록하며 완료되지 않은 사진은 원본 조회를 유지한다.
- 최초/재진입·창 복귀·주인/비회원/타 홈 회원에서 기준 측정과 같은 조건으로 실측한다. 운영 사진 수/크기 차이, 캐시와 느린 첫 요청을 구분한다.
- 기존 데이터/원본 보존, 실제 제공 파일 해시, 파생 파일 보호, 기존 로그인/쓰기 동작을 확인한다. 운영 데이터를 테스트 목적으로 임의 삭제하거나 관계를 끊지 않는다.
- 설치 배포본을 최종 소스로 다시 생성하고 배포 커밋·Actions·측정/보존 결과를 기록한다. Git 변경을 커밋·정리한다.

완료 기준: A/B 정상 배포와 실제 개선 확인, 기존 데이터/원본 보존, 보호/호환 검사, 최종 설치 산출물 및 기록 완료. 실패한 하위 작업이 있으면 Step 13을 완료로 표시하지 않는다.
