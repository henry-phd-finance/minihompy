# 메뉴 로딩 성능·권한 계약

2026-09-26 Step 1 확정. 구현은 이후 단계에서 진행한다. 중앙 서버 변경은 현재 범위에 필요하지 않다.

## 측정

- 같은 1280×900 Chromium에서 사이트/역할별 첫 메뉴 진입과 재진입을 각각 측정한다. 최초 중앙 사용자 확인과 로그인은 측정 구간 밖이다. 첫 측정을 서버 콜드 스타트라고 단정하지 않는다.
- 클릭 직전부터 실제 본문 요소(또는 명시적 빈 목록)가 표시되는 첫 프레임을 `firstBodyMs`로 기록한다. 사진은 실제 이미지 디코딩 완료(`complete && naturalWidth`) 후 보이는 첫 사진과 전체 사진 완료를 별도 기록한다. 로딩 안내만 숨기는 것은 완료가 아니다.
- 달력 준비 시간은 본문 시간과 구분한다. 최신 글 도입 이후 처음에는 `latest` 결과로 날짜를 확정하고 본문을 표시하며 해당 월 달력 조회는 본문을 막지 않는다. 날짜를 이미 아는 직접 선택 경로에서는 달력/본문을 병렬 조회한다.
- 댓글은 본문 후 독립적으로 로딩되므로 본문 완료 기준에 포함하지 않는다. 구간 안에 시작한 관련 요청은 별도 집계한다. 메뉴 전환 시 직전 메뉴에서 발생한 요청이 섞일 수 있으므로 경로/시작 시각을 함께 보존한다.
- 기록에는 허용 목록의 endpoint 경로, 메서드, 상대 시각, 상태, 건수만 남긴다. 쿼리 문자열·헤더·요청/응답 본문·토큰·개인 콘텐츠·스크린샷은 남기지 않는다.
- 로컬 고정 지연 fixture는 실제 view/repository/content-access/photo-media 코드를 사용한다. Auth/전송/댓글은 대역이며 권한 보안의 증거가 아니다. SQL·API·경합 검증은 별도로 수행한다.
- 지연(ms): auth 단계별 20, 폴더 40, health 100, 달력 250, 목록 100, 빠른 사진 80, 느린 사진 600. 비회원/주인/일촌/비일촌/빈 목록 각각 첫 진입·재진입 비교. 향후 날짜/권한 시나리오를 추가해도 기존 지연 프로필은 유지한다.

## 준비 상태 재사용 — Step 2

- 키: 개인 서버 URL + 사이트 ID + 프로토콜/배포 식별자(있는 경우). 메모리에만 보관하고 새 페이지에서는 새로 확인한다.
- 완전한 정상 응답만 **수신 시점부터 30초** 재사용한다. 성공이 아닌 응답과 404 legacy 판별은 성공 캐시에 저장하지 않는다. 같은 키의 진행 중 health는 하나로 합친다.
- 모든 대기자는 자신의 메뉴/인증 세대를 검사한다. 한 대기자가 메뉴를 떠나도 다른 유효한 대기자의 공통 요청을 취소하지 않는다. 공통 요청 자체에는 시간 제한을 둔다.
- 설정/서버/배포 키 변경, 명시적 재시도, 준비 상태 불일치·지원 프로토콜 변경·서버 준비 오류 때 캐시를 폐기한다. 삭제된 글의 정상적인 NOT_FOUND와 서버 미지원/장애는 구분한다.
- TTL은 배포 기능 안내의 재사용일 뿐 읽기 허가가 아니다. 실제 콘텐츠/파일 API의 준비 상태 및 권한 검사는 매 요청 계속 수행한다. health가 성공했다고 콘텐츠 오류를 공개 조회로 우회하지 않는다.

## 주인 인증 재사용 — Step 3

- 최초 로그인·세션 복원·다른 사용자 또는 새 인증 세션 전환 때 서버의 주인 확인을 한 번 수행한다. 동시에 시작된 확인은 합친다. 검증 전에는 주인 UI/쓰기 컨텍스트를 부여하지 않는다.
- 같은 사이트·사용자·검증된 Supabase 세션에서 결과를 재사용한다. SDK의 현재 세션/사용자/만료/세션 식별자와 로컬 인증 세대를 확인한다. SDK에서 읽은 클레임은 로컬 불일치 감지용이며 서버 권한 증거로 사용하지 않는다.
- 같은 세션의 정상 토큰 갱신은 매번 getUser/주인 RPC를 발생시키지 않는다. 요청에는 갱신된 현재 토큰을 사용한다. 중앙 작성 세션의 15분을 주인 유효기간으로 사용하지 않는다.
- 로그아웃·다른 탭 변경·세션 부재·다른 사용자/세션·갱신 실패·인증 거절 시 해당 검증 상태와 진행 중 결과를 무효화한다. 권한 변경은 실제 서버 요청에서 강제하고 거절 시 UI를 정리한다. 로컬 캐시만으로 원격 권한 회수를 즉시 안다고 가정하지 않는다.
- 데이터 요청 전후의 세대/사용자 일치 검사와 늦은 응답 폐기를 유지한다. 서버 토큰 검증, owner RPC/RLS, 보호 파일의 다운로드 전후 권한 검증은 이 단계에서 제거하지 않는다.
- 글 하나의 접근 거절과 인증 자체의 거절을 오류 코드로 구분한다. 모든 403을 무조건 전체 로그아웃으로 처리하지 않는다. 재검증/토큰 갱신 재시도는 요청당 한 번으로 제한하고 실패 시 중단한다.

## 다이어리 최신 글 — Step 4

- 기본 폴더 진입과 폴더 변경은 **현재 방문자가 읽을 수 있는 가장 최신 일기 날짜**를 기본 선택한다. 최신 기준은 일기의 `entry_date`, 같은 날짜에서는 기존 시간/ID 정렬을 유지한다. 작성/수정 시각으로 과거 날짜의 일기가 앞으로 뛰지 않는다.
- 첫 요청 하나에서 그 날짜의 최신 글이 포함된 페이지·건수·선택 날짜를 함께 받는다. 날짜만 찾으려고 별도 요청하거나 전체 글을 내려받지 않는다. 기본 첫 진입에서는 기존 오름차순 정렬을 유지하면서 해당 날짜의 마지막 페이지를 반환하고, 마지막 시간/ID의 글에 초점을 맞춘다. 선택 날짜만 최신이고 최신 글이 다른 페이지에 숨는 상태를 허용하지 않는다.
- API는 `content/list`의 diary 전용 `latest: true` 선택자를 추가한다. `date/month`와 동시 지정 금지. 최신 선택·권한 필터·글 조회를 같은 DB 스냅샷에서 처리하고 `selected_date`, 최신 대상/실제 페이지와 기존 목록 데이터를 반환한다. 일촌/비공개 제외 후 최신을 결정한다. 숨겨진 글의 날짜·건수도 노출하지 않는다.
- 해당 응답을 바로 표시하고 달력은 반환 날짜의 월로 맞춘다. 그 월의 날짜 표시는 독립적으로 조회하며 늦게 와도 본문을 가리지 않는다. **월을 모르는 첫 진입에서 달력과 최신 글 요청이 완전히 병렬이라고 주장하지 않는다.** 미래 일기 입력은 기존 작성 허용 범위를 유지하므로 최신 날짜 비교에도 포함한다.
- 직접 날짜 선택은 선택 날짜를 유지하고 달력/본문을 병렬로 가져온다. 특정 글 주소 진입은 그 글/폴더/날짜/페이지가 우선이다. 빈 폴더는 한국 시간 이번 달 달력과 빈 목록, 새 작성 날짜는 한국 시간 오늘이다.
- 달력만 실패하면 날짜 표시를 오류/재시도 상태로 두고 성공한 본문은 유지한다. 전역 인증/관계 무효화는 본문도 정리한다. 폴더·날짜 빠른 변경에서 이전 응답을 반영하지 않는다.
- 신규 capability `diary_latest_protocol: 1`은 해당 SQL/API가 준비됐을 때만 health에 추가한다. 구 UI는 추가 필드를 무시한다. 구 서버/SQL에서는 기존 날짜 선택 동작을 유지하고, 미지원 여부를 임의의 403/500으로 추측하거나 공개 권한으로 우회하지 않는다. 새 UI/서버/SQL 모두 배포된 A/B는 최신 글 동작이 필수다.

## 사진 메타데이터 재검증 — Step 5

- 빈 목록이나 사진 다운로드 대기가 없는 결과는 최초 권한 검사된 목록으로 표시한다. 똑같은 전체 목록을 즉시 다시 요청하지 않는다.
- 기존 `content/detail`은 본문 전체와 권한 확인을 글마다 다시 전송하므로 최종 목표로 쓰지 않는다. **소수 글을 묶는 `content/photo-check` 경로**를 추가한다. 요청은 최대 2개 글(현재 페이지 크기), 글별 ID와 기대 revision만 받는다. 임의 SQL/테이블/Storage 경로 입력은 받지 않는다. 몸체 상한은 기존 8KB 이내다.
- 서버는 현재 모드·일촌 관계·글 가시성 검증을 거쳐 요청한 각 글의 존재/버전 일치만 반환한다. 불허/삭제/변경은 `valid: false`로 통일하고 현재 revision·본문·숨겨진 파일 경로는 돌려주지 않는다. 검증된 revision은 사진 body 변경 때 반드시 증가함을 SQL 테스트로 확인한다.
- API/SQL의 read-context는 `content.photo-check` action과 최대 2개 ID·기대 revision 집합을 바인딩한다. Step 5에서 실제 중앙 계약을 확인해 구체화했다: 중앙은 action별 API가 아니라 불투명한 request_hash를 서명하므로 중앙 변경 없이 배치 전체에 신선한 read-context 1회를 발급한다. 개인 SQL은 기존 friend_read_authorize를 사용하고 각 대상의 현재 가시성·revision·이미지 연결을 검사한다. 기존의 대상별 detail 어댑터 구상보다 왕복이 적고, 요청 집합 전체가 동일 권한 문맥과 기한에 묶인다.
- capability `photo_check_protocol: 1`을 모든 필요한 SQL/API가 준비됐을 때 health에 추가한다. 없으면 기존 전체 목록 최종 재조회 경로를 유지한다. 인증/권한 오류를 미지원으로 취급하지 않는다.
- 보호 파일 API의 바이트 무결성 및 다운로드 전후 최신 권한 검사는 유지한다. 메타데이터 검증도 관계/세션 경합 조건을 보존한다. 응답 수신 이후 발생한 모든 원격 변경을 즉시 감지한다고 보장하지 않는다.

## 사진 점진 표시 — Step 6

- 최신 권한 검사된 목록으로 틀/본문을 먼저 표시한다. 사진은 빈 자리를 확보하고 읽기 API 완료·디코딩·현재 글 revision/세대 확인을 거쳐 준비된 단위부터 붙인다.
- 글별 다운로드 중 일부가 완료되면 검증을 요청할 수 있다. 같은 시점에 준비된 글은 묶고, 검증 진행 중 추가로 도착한 사진은 그 검증 시작 전에 준비됐는지 구분한다. 이전 사진을 위해 한 검증을 나중에 끝난 다운로드에 무기한 재사용하지 않는다. Step 5 최대 2개 묶음 제한과 기존 다운로드 동시성 4 유지.
- 느린 사진이 다른 준비된 사진 표시를 막지 않는다. 화면 가까운 사진을 우선하고 전체 완료 시간도 같이 기록한다. 본문만 빨라지고 전체 요청이 폭증하면 개선 완료로 판단하지 않는다.
- 개별 파일 손상/실패는 해당 사진 재시도, 글 변경은 해당 글과 댓글 정리·재조회, 인증/일촌 무효화는 전체 보호 콘텐츠/URL 정리. 댓글은 글마다 한 번 연결한다.
- 이미 준비된 결과도 메뉴 이탈·계정 변경·visibility 무효화 후에는 표시하지 않는다. AbortController, Blob URL 해제, 스크롤/직접 글 주소를 유지한다.

기존 테스트가 의도적으로 전체 화면 대기를 전제하면 새 동작에 맞춰 기대값을 고치되 권한 경합과 누출 금지 검사는 유지한다. Step 1은 향후 성능 수치를 미리 통과시키는 테스트를 작성하지 않고 현재 기준값과 별도 권한 회귀만 확인한다.
