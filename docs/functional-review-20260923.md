# A 사용자 관점 기능 검토 — 2026-09-23

## 검토 범위

실제 A 계정으로 로그인해 A/B GitHub Pages의 홈·프로필·다이어리·사진첩·게시판·방명록과 A의 설정을 조회했다. Chromium 1280×820에서 확인했다. 기존 콘텐츠 등록·수정·삭제 및 설정 저장은 하지 않았다. 종료 시 A의 개인 로그인과 중앙 로그인을 해제했다. 쓰기 성공 여부를 검증한 리뷰는 아니다.

- A: https://henry-phd-finance.github.io/minihompy/
- B: https://henry-hs-jung.github.io/minihompy/
- A에서 로컬 관리자, B에서 일반 방문자로 구분됨을 확인했다.
- 아래는 실제 화면 관찰과 현재 구현 코드를 대조한 결과다. 개선안은 아직 구현하지 않았다.

## 권장 순서

### 1. 중앙 회원과 방명록·댓글 작성자 연결

실제 B 상단에는 A의 이름이 표시되지만 방명록·댓글 이름 입력란은 비어 있고 수정 가능하다. `MinihompyVisitorSession.context()`는 B에서 reader/userId 없음으로 반환됐다.

`visitor-session.js`, `visitor-identity.js`, `guestbook-repository.js`, `comments-repository.js`의 쓰기 경로는 중앙 회원 대신 해당 개인 Supabase의 익명 인증을 사용한다. 작성자 소유권도 개인 프로젝트의 author_id 기준이다. 따라서 다른 브라우저에서 A로 다시 로그인하는 것만으로 기존 익명 작성자의 수정·삭제 권한을 복원하는 구조가 아니다.

필요한 작업:
- 개인 서버가 검증한 중앙 회원 ID를 작성자에 연결하고 이름·홈페이지 링크를 제공한다.
- 비밀글 읽기 및 수정·삭제 권한도 같은 검증된 회원에 연결한다.
- 계정 전환·로그아웃 시 이전 작성자 권한이 남지 않게 한다.
- 기존 익명 글은 중앙 회원 소유로 임의 이전하지 않는다. 비회원 작성을 유지할지 정책을 정한다.

이름 자동 입력만으로 해결할 수 없으며 개인 API/DB의 권한 검증까지 필요하다.

### 2. 기본 이동 및 실제 상태 표시

`index.html`의 내 미니홈피·랜덤, `views/home.js`의 파도타기는 실제 이동 기능이 없는 표시 요소다. B에서 내 미니홈피를 눌러 A로 돌아오는 기능, 작성자 이름/집 아이콘을 통한 방문 기능이 필요하다.

본인 사이트에서도 일촌맺기와 고정 관계 문구 '사촌'이 표시된다. 본인/타인/비로그인 상태와 실제 관계를 구분해야 한다. 두 사이트의 표시 이름이 같더라도 계정·사이트는 다르므로 핸들과 사이트 소유자를 구별해 보여주는 것이 좋다.

### 3. 홈 데이터를 실제 게시물과 연결

A의 게시판과 사진첩에는 각각 실제 글이 있지만 홈은 게시물이 없다고 표시하고 건수는 0/0이다. 방명록도 실제 여러 글과 홈 건수가 맞지 않는다. `views/home.js`의 건수는 고정값이다.

최근 공개 게시물·새 댓글·메뉴별 건수를 조회하고 해당 글로 이동할 수 있어야 한다. TODAY/TOTAL은 현재 설정에서 수동 입력하는 값이므로 방문 집계와 분리하거나 실제 집계를 구현한다. 비공개 글의 제목·건수가 공개 홈에서 새지 않도록 한다.

### 4. 주인의 콘텐츠 관리 완성

A 게시판의 폴더관리하기는 실제 disabled 상태다. 사진첩 폴더관리와 다이어리 관리하기는 표시만 있다. 폴더 생성·이름 변경·정렬·삭제 및 글 이동 UI가 필요하다. 글이 있는 폴더 삭제 규칙도 필요하다.

현재 게시판·사진첩·다이어리는 공개 중심이다. 공개/나만보기부터 구현하고, 일촌 공개는 관계 기능 이후 구현한다. 방명록의 비밀글 기능은 이미 있으므로 일반 게시물 공개범위 기능과 구분한다.

### 5. 일촌 기능

일촌신청·일촌평·팬·관계 표시는 현재 관계 데이터와 연결되지 않았다. 신청/수락/거절/취소/끊기, 일촌 목록 및 방문, 일촌평과 삭제 권한이 필요하다. 관계 데이터의 보관 위치와 양쪽 사이트의 동기화 방식을 먼저 결정한다.

### 6. 작성 중 이동 보호 및 글 주소

코드상 `app.js`의 탭 전환에는 공통 이탈 확인 절차가 없고 각 작성 화면의 beforeunload는 같은 문서 내 탭 이동을 보호하지 않는다. 화면별 초안 유지 방식도 다르다. 공통 저장 전 이탈 확인/임시저장과 저장 후 복귀를 정리한다. 이 항목은 실제 초안을 입력해 소실을 재현한 결과가 아닌 코드 검토 사항이다.

현재 메뉴 중심 주소를 글 단위 주소로 확장하면 최근게시물·알림·공유 링크에서 원하는 글을 직접 열 수 있다.

### 7. 빈 메뉴와 표시뿐인 기능 정리

- 프로필: 소개 외 키워드·히스토리·42문답·기본정보·인맥·즐겨찾기는 코드상 본문이 비어 있다.
- 사진첩: 작게보기·슬라이드·스크랩은 동작이 연결되지 않았다.
- 검색: 실제 입력과 버튼이 disabled다.
- 쥬크박스·갤러리·동영상: 설정에서는 노출할 수 있으나 뷰는 빈 문서 조각이다.
- BGM·미니룸 편집·선물: 화면 표현 중심으로 실제 기능이 필요하다.

미구현 기능은 숨기거나 준비 중임을 명시하고, 핵심 사용 흐름 이후 순차 구현한다.

### 8. 상호작용 이후 알림·운영

댓글/답글·방명록·일촌신청 알림과 읽음 처리, 사용자 차단 및 반복 작성 제한을 추가하면 실제 교류를 운영하기 쉬워진다. 구현 시 콘텐츠는 각 개인 DB에 두고 중앙에 필요한 최소 이벤트만 둘지 설계한다.

## 우선 구현 묶음 제안

첫 묶음은 작성자 연결, 내 미니홈피/작성자 방문, 홈 실제 데이터다. 다음은 폴더/공개범위 관리와 일촌이다. 미니룸·BGM·선물은 그 다음으로 둔다. 화면 크기 조정은 사용자 요청대로 이번 검토의 구현 우선순위에서 제외했다.
